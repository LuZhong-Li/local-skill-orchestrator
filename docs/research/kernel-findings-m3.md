## 0. 方法与边界

- 探针用**真实命令行入口**（`kernel/entry/cli.ts`）在系统临时目录造最小工作区，逐条记录退出码、问题码（含 `target`）、索引记录与 `--json` 原始 findings；工作区用后即删。

## 1. 观察项 1：环检测问题码在收敛轮不可见、级联扩散

### 1.1 现状（探针实测）

工作区：`a` 依赖 `b`、`b` 依赖 `a`（环）、`c` 依赖 `a`（下游）。

| 指令 | 退出码 | 错误级 findings | 索引内运行期结论 |
|---|---|---|---|
| `scan`（写索引） | **1** | `E-VALIDATION-002@b.dependencies`、`E-VALIDATION-002@c.dependencies` | `a: ok`、`b: invalid`、`c: invalid` |
| `validate`（紧随其后） | **1** | `E-VALIDATION-002@a.dependencies` + `W-INDEX-002` ×3 | — |

**两个直观症状**：

1. **环本身不可见**：任何一次输出里都没有 `E-DEP-003`；
2. **扫描的结论与实时复核互相矛盾**：`scan` 说 `a` 可用、`b/c` 不可用；`validate` 立刻说 `a` 依赖未满足，并**对所有三条记录**报 `W-INDEX-002`（「运行期结论已过期」）——刚扫完就全过期。

### 1.2 逐轮状态（复刻 `scanWorkspace` 的循环）

| 轮次 | 进入时的 availability | 该轮 findings | 算出的下一轮 availability |
|---|---|---|---|
| 0 | a,b,c 全 true | `E-DEP-003@a` | a=false, b=true, c=true |
| 1 | a=false | `E-VALIDATION-002@b`、`@c` | a=true, b=false, c=false |
| 2 | a=true, b/c=false | `E-VALIDATION-002@a` | a=false, b=true, c=true |
| 3 | a=false | `E-VALIDATION-002@b`、`@c` | a=true, b=false, c=false |

循环上限是「候选数 + 1」轮（3 个候选 → 第 0~3 轮），第 3 轮算完后**不再使用**其 `recomputed`，但**用它这一轮的 findings 写索引** → 于是索引结论（a ok / b,c invalid）与最后一轮进入时的 availability（a=false）不一致。**状态在 (a=false,b/c=true) 与 (a=true,b/c=false) 之间振荡**，最终落点是「轮数奇偶」而不是语义。

**决定性证据（结果依赖技能总数）**：同一份依赖结构，只额外加一个**互不相干**的技能 `d`：

| 候选数 | 最后一轮用于写索引的 findings |
|---|---|
| 3（a,b,c） | `E-VALIDATION-002@b`、`@c` |
| 4（a,b,c,+d） | `E-VALIDATION-002@a` |

也就是说，**多加一个无关技能会让「谁不可用」翻转**——这不是业务语义，是收敛判据的产物。

### 1.3 代码位置

| 位置 | 作用 |
|---|---|
| `kernel/core/discovery/index.ts:84-103` | 不动点循环：每轮用「当前 availability」算 findings，再用 findings 算 `recomputed`；相等即停 |
| 同文件 `:105-112` | 用**最后一轮**的 findings 按 owner 归并，作为写索引的问题清单 |
| 同文件 `:439-445` `sameAvailability` | 严格逐键相等——不检测「是否单调下降」 |
| `kernel/core/metadata/validate.ts:474-513` `validateDependencies` | 依赖判定 + `edges` 只收「当前可用」的边 |
| 同文件 `:520-545` `findCycles` / `detectCycles` | 环在**当前可用图上**检测；环问题码 `E-DEP-003` 的 `target` 是 `cycle[0]` |

关键点：**环问题码是「当前轮」的产物，不是结构性事实**——下一轮环上某条边因「被依赖方不可用」被剔除，环就消失了，环问题码也随之消失；而依赖级联又可能把记录翻回可用，于是振荡。

### 1.4 契约比对

| 契约原文 | 与本现象的对照 |
|---|---|
| `index-format.md:99`：「登记与刷新…**并重新计算运行期结论**」；`:109`：「运行期结论只由登记与刷新动作写入或刷新」 | 扫描写结论 ✓；但未规定「写下的结论必须与一次新的实时判定一致」 |
| `index-format.md:178`：「结论时效 \| 运行期结论是否由最近一次扫描产生 \| 索引类警告」；`:184`：「当判定结论已过期时，校验在报告中提示『建议重新扫描』」 | `W-INDEX-002` 的语义是「与实时判定不一致」→ **刚扫完就不一致**，等于扫描没有完成它被要求的职责 |
| `result-and-exit-codes.md:195`：`W-INDEX-002`「索引中的运行期结论已过期，建议重新扫描」 | 同上 |
| 需求 `CON-04` 裁决（`requirements.md:2101-2107`）：运行期结论的承载与写入权限 | 只定「谁写」，**未定「环应该如何被报告」** |
| `skill-meta-spec.md` V-12/V-13、`result-and-exit-codes.md:281`（V-13 → `E-DEP-003`） | 环是**错误级**问题，规范承认它必须被报告；现状是「算了但没报」 |
| `result-and-exit-codes.md:322` 第 6 步：`DEP`/`RUN` 类 → **退出码 6** | 环一旦可见，`scan` 的退出码将从 1 变成 6（见 4.2 影响面） |

### 1.5 判定

**实现缺陷 + 契约缺口（两者都有）**：

- **缺陷**：收敛判据假设「可用性只可能由 true 翻 false」（代码注释也这么写），但环问题码的**轮内消失**让记录能翻回 true → 振荡；停止时机又把「上一轮的输入」与「最后一轮的输出」混用 → 索引结论与实时判定矛盾，且结论随候选数量奇偶翻转。
- **契约缺口**：契约没有规定「环的报告形态」（每个环成员各报一次？只报环首？下游如何级联？）与「扫描结论必须可被紧随的校验确认」这条不变量。

### 1.6 修复候选

| 候选 | 做法 | 优点 | 风险/代价 |
|---|---|---|---|
| **A（推荐）环在收敛前一次性定为不可用** | 用**全部候选的元数据图**（不看可用性）先做环检测，把环成员标记为「永久不可用」；进入不动点后可用性只降不升 | 恢复单调性（循环的前提成立）；环成员稳定带 `E-DEP-003`；下游稳定带 `E-VALIDATION-002`；结果与 N 无关 | 环检测从「每轮」改为「一次」，实现改动集中在 `scanWorkspace` 前置段；`validate` 侧需同源（复用同一函数） |
| B 收敛轮 findings 与初始轮合并（粘性） | 把每轮 findings 求并集，环问题码不会消失 | 改动小 | 仍需保证可用性单调（不能靠并集掩盖翻回），且矛盾 findings 可能同时存在（同一技能既环又级联） |
| C 只保留初始轮环问题 | 初始轮 findings 单独保留、追加到最终清单 | 最小改动 | 若环成员在中间轮被翻回可用，索引结论仍可能自相矛盾（治标） |

**建议的预期语义（供拍板）**：

1. 环上每个技能都带 `E-DEP-003`（`target` 为自身），`deps` 的 `cycles` 与之一致；
2. 直接/传递依赖环上技能的记录带 `E-VALIDATION-002`（级联可见，且不吞掉根因）；
3. **`scan` 写下的结论必须与紧随其后的 `validate` 实时判定一致**（不出现「刚扫完全过期」）；
4. 结果与工作区技能总数无关（同一子图在 N=3 与 N=4 下结论相同）。

## 2. 观察项 2：技能元文件的 YAML 错误落到退出码 3（「索引损坏」档）

### 2.1 现状（探针实测）

工作区含一个元文件 YAML 损坏的技能（`broken`）与一个正常技能：

| 指令 | 退出码 | finding 原文 |
|---|---|---|
| `scan` | **3** | `{"code":"E-YAML-001","severity":"error","source":"meta","target":"broken",…}` |
| `validate` | **1** | （专属口径：存在错误级问题即 1） |

`categoryOf('E-YAML-001')` = `YAML` → 命中的是派生规则第 3 步（`VER`/`INDEX`/`YAML` → 3）。

### 2.2 代码位置

| 位置 | 作用 |
|---|---|
| `kernel/dispatch/result/index.ts:25-35` `exitCodeFor` | `if (categories.has('VER') \|\| categories.has('INDEX') \|\| categories.has('YAML')) return 3;` ——**只看类别，不看对象** |
| `kernel/store/contract.ts:152-155` `categoryOf` | 从问题码第二段取类别 |
| `kernel/core/discovery/index.ts`（元文件解析失败处） | 元文件 YAML 解析失败 → `E-YAML-001`，`source: 'meta'` |

### 2.3 契约比对

| 契约原文 | 说明 |
|---|---|
| `result-and-exit-codes.md:322` 第 3 步：「存在问题码属于 `VER`、`INDEX` 或 `YAML` 类别，**且问题对象为索引或配置文件时**，退出码为 `3`」 | **有明确的对象限定** |
| 同文件 `:337` 映射表：「`VER`、`INDEX`、`YAML`（**作用于索引或配置文件**）」 | 同上 |
| 同文件 `:308-314` 退出码语义：`3` = 「索引或配置文件损坏，或版本不受支持」；`1` = 「通用失败或校验未通过」 | 技能元文件损坏属「校验未通过」→ 1 |
| `result-and-exit-codes.md:186` / `skill-meta-spec.md` V-09 | `E-YAML-001` 适用对象包含技能元文件（问题码本身没错，错的是**退出码派生**） |

### 2.4 判定

**实现缺陷（契约已规定，无需补条文）**：类别命中后缺少对象判定，导致技能级 YAML 错误被归入「索引/配置损坏」档。

同一数据下 `scan` 返回 3、`validate` 返回 1，也说明**派生规则的实现与指令专属口径不一致**——用两个指令看同一环境会得到「索引坏了」与「只是校验不通过」两种结论。

### 2.5 修复候选

`exitCodeFor` 增加**对象判定**：`YAML`（以及 `INDEX`/`VER`，若将来出现技能级同类别码）只有作用于**索引或配置文件**时才计入 3 档。最小落地方式：

1. 用 finding 的 `source` 作对象代理：`source === 'meta'` 的 `YAML` 不计入 3 档（元文件问题 → 落到第 7 步 → 1）；`source === 'config'`（配置区）与索引版本类（`source: 'registry'`、`target: 'schema_version'`）仍计入 3。
2. 若要更严格：在 `Finding` 上显式引入「对象类别」字段（`skill` / `index` / `config` / `workspace`），派生规则直接读它——**这是结果规范的字段变更**，需走契约批次。

推荐先做 1（不改契约、可断言），并补单测：`source:'meta'` 的 `E-YAML-001` → 1；`source:'config'` 的 `E-YAML-001` → 3；`VER`（索引版本）→ 3。

## 3. 观察项 3：目录名与 id 不一致导致索引重复记录、误报 `E-ID-002`

### 3.1 现状（探针实测）

工作区只有一个技能：目录 `foo`，元文件 `id: bar`（`path` 按目录写为 `./skills/foo`）。连续扫描：

| 轮次 | 退出码 | 索引记录数 | 记录 id | 备注 |
|---|---|---|---|---|
| 第 1 次 | **1** | 1 | `bar` | 该记录带 `E-FIELD-002`（落位路径与目录不符）+ `E-ID-003`（id 与目录名不一致） |
| 第 2 次 | **3** | **2** | `bar`、`bar` | 第二条是「磁盘上已不存在」，带 `E-INDEX-002` |
| 第 3 次 | 3 | 2 | `bar`、`bar` | 稳定在 2 条（Map 去重，不无限增长） |
| `validate` | 1 | — | — | `E-ID-002`（标识出现多次）、`E-PATH-001`（索引记录指向 `skills/bar` 不存在） |

**症状**：索引违反自身不变量（同一标识两条记录），用户看到的是「标识重复」而不是根因「id 与目录名不一致」；`scan` 的退出码还被 `E-INDEX-002`（INDEX 类）推到 3。

### 3.2 代码位置

| 位置 | 作用 |
|---|---|
| `kernel/core/discovery/index.ts:68` | `const existing = new Map(index.skills.map((record) => [record.id, record]))` ——**以记录 id 为键** |
| 同文件 `:139` | `existing.delete(candidate.dirName)` ——**以目录名删除** |
| 同文件 `:152-171` | 剩余 `existing` 记录被追加为「磁盘上已不存在」（`E-INDEX-002`） |

两条键策略不一致：`foo`（目录名）永远删不到 `bar`（记录 id），于是每轮都多写一条「已不存在」的副本。

### 3.3 契约比对

| 契约原文 | 说明 |
|---|---|
| `skill-meta-spec.md:45`：「**Skill ID**…取值**等于该 Skill 目录名**」；`:69`；`:80`：「Skill ID 必须与所在目录名完全一致（大小写敏感）」 | **id = 目录名是硬约束**，不一致本身是错误状态，不是受支持的情形 |
| `skill-meta-spec.md:201`（字段表）：`id`「必须与所在目录名完全一致」 | 同上 |
| `skill-meta-spec.md:401-403`（V-02/V-03）：「索引内不得出现重复 `id`；索引中的每个 `id` 必须能在 `./skills/` 下找到同名目录；目录名必须与 `id` 完全一致」 | 现状同时违反 V-02 与 V-03 的**报告与不变量** |
| `index-format.md:81`（2.3 不变量第 2 条）：「记录区内每个记录的标识在索引内唯一」 | 现状（两条 `bar`）**违反索引的文件级不变量** |
| `result-and-exit-codes.md:180`（`E-ID-003`）、`:281`（V-03） | 根因已有专用问题码 |

### 3.4 判定

**实现缺陷（契约已规定）**：`id ≠ 目录名` 是**应被拒绝并报告的异常**（`E-ID-003`），但索引仍必须保持不变量（标识唯一）。现状把「异常」扩散成了「索引损坏」（重复记录 + 误导性的 `E-ID-002`/`E-INDEX-002`）。

补充：`install` 的落位目录按 id 生成（`skills/<id>`），所以 `id ≠ 目录名` 只会来自**手工创建/改名**；即便如此，扫描也必须正确报告且不破坏索引。

### 3.5 修复候选

**以目录名作为「记录归属」的键**，id 仍取元文件的值（保持现状的投影语义）：

1. 建立 `existing` 时用**目录名**作键——索引记录本身没有目录名字段，但 `path`（`./skills/<目录名>`）可稳定推导；或在 `scanWorkspace` 内维护 `dirName → record` 的映射（由 `path` 解析）。
2. 候选记录按同一键删除/更新 → `foo` 的记录不会被误判为「已不存在」，第二次扫描起稳定为 1 条。
3. `E-ID-003` 依旧由元数据校验产生（技能级错误，退出码 1）；不再出现 `E-INDEX-002`/`E-ID-002` 噪声。

**影响面**：`install`/`enable`/`disable` 的落位不受影响（它们本来就按 id 建目录）；`export` 会导出修正后的索引（少一条重复记录）；`deps` 按 id 解析依赖，行为不变（id 仍是元文件的值）。

**需拍板的一个细节**：`path` 字段与目录名不一致时（例如 `path: ./skills/other`），修复后的「归属键」仍应以**实际目录名**为准（目录是磁盘事实），而 `path` 的不一致继续由 `E-FIELD-002` 报告——本报告的复现里两者同时存在，正是这种情况。

## 4. 影响面汇总与拍板项

### 4.1 三项修复对指令的影响

| 指令 | 观察项 1 | 观察项 2 | 观察项 3 |
|---|---|---|---|
| `scan` | 环成员与下游的问题码稳定可见；结论与实时判定一致；退出码可能由 1 → **6**（见 4.2） | 技能元文件 YAML 错误由 3 → **1** | 不再产生重复记录与 `E-INDEX-002`；退出码由 3 → 1（只剩 `E-ID-003`） |
| `validate` | 不再对刚扫过的记录报 `W-INDEX-002`（结论一致） | 不变（专属口径已是 1） | 不再报 `E-ID-002`/`E-PATH-001`（记录唯一且指向真实目录） |
| `export` | 导出物携带一致结论 | 不变 | 不再导出重复记录 |
| `deps` | 环列表与索引一致（`E-DEP-003` 可见） | 不变 | 不变 |

### 4.2 需要拍板的点

| # | 决策点 | 选项与我的建议 |
|---|---|---|
| ① | 环的报告形态 | **建议**：环上每个技能各带一次 `E-DEP-003`（`target` 为自身），下游带 `E-VALIDATION-002`；`deps` 的 `cycles` 与之一致。**备选**：维持现在的「只报环首一次」（信息不完整，不建议） |
| ② | 环可见后 `scan` 的退出码 | 按 §5.2 第 6 步应为 **6**（`DEP` 类）；但指令契约的扫描小节写着「按第 5.2 节的派生规则返回退出码 1」——**建议**以派生规则为准（6），并在扫描小节把「返回 1」改成「按派生规则」。若倾向保持 1，需要给 `scan` 增加专属口径（属契约变更，需登记） |
| ③ | 收敛策略 | **建议 A**：环在一次结构检测里定型（不可用），之后可用性单调下降；**备选 B**：收敛轮 findings 与初始轮合并（粘性）。两者都要保证「结果与 N 无关」 |
| ④ | 元文件 YAML 的退出码 | **建议**：`source === 'meta'` 的 `YAML` 不计入 3 档 → 落 1；配置文件/索引仍 3。若要显式对象字段，属结果规范变更，另批 |
| ⑤ | `id ≠ 目录名` 的归属键 | **建议**：以**实际目录名**为归属键（`id` 仍取元文件值，作为投影与错误报告的对象）；`path` 不符继续由 `E-FIELD-002` 报 |
| ⑥ | 是否需要新问题码 | 三项都可用现有码（`E-DEP-003`/`E-VALIDATION-002`/`E-YAML-001`/`E-ID-003`）表达，**建议不新增**；若拍板要求「扫描结论不一致」也要可诊断，可考虑新增索引类问题码（属契约批次） |

### 4.3 建议的契约补文（缺口部分）

> **运行期结论的一致性**：扫描动作写下的运行期结论必须与紧随其后的实时判定一致（同一份磁盘内容、同一份索引，不产生 `W-INDEX-002`）；该一致性是扫描「重新计算运行期结论」职责的判定标准。
>
> **依赖环的报告**：构成环的每个技能都携带 `E-DEP-003`；依赖环上技能（直接或传递）的记录携带 `E-VALIDATION-002`；环的存在不因本轮可用性变化而消失。

## 6. T1 修复落地（2026-10-17，六项裁决全部采纳）

### 6.1 三项修复的最终行为（修复后实测）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `a↔b` 环 + `c→a` 下游：`scan` | 退出码 1；`a: ok / b,c: invalid`；环不可见 | **退出码 6**；`a: E-DEP-003`、`b: E-DEP-003`、`c: E-VALIDATION-002` |
| 同一场景：紧随的 `validate` | 归咎 `a` + 三条 `W-INDEX-002` | **与 scan 完全一致**（无 `W-INDEX-002`） |
| 加一个无关技能 `d` | 归咎对象从 `b/c` 翻成 `a` | **结论完全相同** |
| 技能元文件 YAML 损坏：`scan` / `validate` | 3 / 1（同一数据两种结论） | **1 / 1** |
| 索引文件本身损坏：`scan` | 3 | **3**（反向断言保留） |
| 目录 `foo` / 元文件 `id: bar`：重扫 | 第 2 次起 2 条同 id 记录 + 误报 `E-ID-002`/`E-INDEX-002` | **始终 1 条**；只报 `E-ID-003` + `E-FIELD-002` |
| 两目录同一 `id` | — | 显式 `E-ID-002`；记录数 2（物理唯一） |

### 6.2 实现落点

| 文件 | 变更 |
|---|---|

### 6.3 连带项

- **bench 预期码表**：`scan` 的允许退出码由 `[0,1,3]` 改为 `[0,1,6]`（夹具的悬空依赖属 `DEP` 类）；修复后小档实测 `scan`=6、`validate`=1、`export`=0、`startup`=0 ✓。
