## 1. 任务序列

### T0 夹具生成器与阈值登记（实现第一批）

**执行状态**：**已完成（2026-10-16）**。交付：需求 9.4.3 的 N=1000 收紧登记（表内加粗 + 说明第 4 条含改前值 / 改后值 / 依据表与沿革）、变更记录批次与计数校验；设计 §2.1 按实测校正并新增 §2.1.1（差异表）与 §2.1.2（不动点级联）；`scripts/bench/thresholds.mjs`（阈值唯一来源）、`scripts/bench/fixture.mjs`（纯计划 + 落盘，含 `mulberry32` / `allocateExact` / `INVALID_KIND_CODES` / `DISTRIBUTION`）、`scripts/bench/fixture-cli.mjs` 与根 `package.json` 的 `bench:fixture`（`bench` 留 T1，避免悬挂引用）；测试 12 项（单元 8 / 契约 4），总数 420 → **432 项**，全绿。

**实测数字（本机 Windows / Node v24.14.1，落系统临时目录）**：

| 档位 | 文件数（= 3N − 2 × 内容缺失样本数） | 占用 | 生成耗时（plan + write） |
|---|---|---|---|
| N=100 | 298（内容缺失样本 1） | 3,885,168 B（3.7 MiB） | 112 ms（3 + 109） |
| N=1000 | 2968（内容缺失样本 16） | 34,412,270 B（32.8 MiB） | 1083 ms（16 + 1066） |
| N=5000 | 14840（内容缺失样本 80） | 167,426,633 B（159.7 MiB） | **10,589 ms（64 + 10,525）**，满足设计 §1.3 的「≤ 14 s」预判 |

**有效无效数为可推导量**：N=1000 为 129（自身无效：五类无效 80 + 悬空依赖 50 减重叠）+ 5（级联）= **134**；内核 `scanWorkspace` 判定与推导逐条一致（N=100 18/18、N=1000 134/134，零差异），契约与单元测试双向钉住。

**实测发现（F-12 / F-13）**：依赖可用性是**不动点迭代**，且环检测会让级联以半个工作区为代价扩散——初版构造（回绕窗口 + 成环）下 100 个技能里 48 个被判无效，「无依赖的技能被判依赖未满足」这一怪象追根到初始轮次的环判定（环问题码只在初始轮次产生，报告只保留收敛轮的问题清单）。夹具因此改为 DAG + 有界级联。**观察项（不改内核）**：环问题码在收敛后不可见、级联轮数与依赖图深度相关，都会影响 `scan` 的成本与可解释性。

**成本登记**：N=5000 落盘用例约 24 s（本机），全量套件时长由约 10 s 增至约 31 s；CI 不跑该档（裁决 ③）。若本地回路日后难以接受，可把该用例降级为 N=1000 落盘 + N=5000 计划级验证（属口径变更，需先改本文档）。

**未覆盖**：测量器（T1）、双线三档跑测（T2）、基线与报告（T3）按计划推进。

**目标**：给出确定性、可复现、不入库的规模夹具，并把 N=1000 的收紧阈值按变更批次登记进需求文档（先文档后实现）。

**依赖**：设计定稿（本文档 + 设计文档第 2 节）。

**交付物**：

1. **文档前置（先于脚本落地）**：需求 9.4.3 表 N=1000 行与表下注修订（含改前值 / 改后值 / 依据表与沿革）、变更记录追加批次与计数校验、CHANGELOG 条目；设计 §2.1 按实测校正（F-9 / F-10）与 §2.2 文件数公式（F-11）；
2. `scripts/bench/fixture.mjs`（纯函数模块）：`planFixture({ seed, n })` 先产出**结构计划**（每个技能的合法性、描述长度档、资产清单、依赖边），`writeFixture(plan, root)` 再落盘；导出 `mulberry32` 与冻结的 `DISTRIBUTION` 常量；
3. `scripts/bench/thresholds.mjs`：三档阈值常量（**唯一来源**，供测量器判定与文档一致性断言共用）；
4. `scripts/bench/fixture-cli.mjs`（命令行入口）与根 `package.json` 的 `bench:fixture` / `bench` 脚本（npm 脚本，**不是** CLI 指令，指令数仍为 16）；
5. 测试：`tests/unit/bench-fixture.test.ts`、`tests/contract/bench-thresholds.test.ts`。

**验收标准（可验证）**：

1. 同种子 + 同参数 → `planFixture` 结果深度相等，且落盘文件集合与**逐文件内容哈希**一致（幂等 / 确定性）；换种子 → 结构不同（反例）；
2. 规模：文件数按 F-11 的公式精确核对（N=1000 为 `3000 − 2 × 内容缺失样本数`），占用与设计 §1.3 同量级（N=1000 约 32 MB、N=5000 约 160 MB）；生成耗时单列（不计入测量），执行状态回填实测数字；
3. 分布断言：合法 / 合法带警告 / 无效 = 87% / 5% / 8%（精确配额）；无效五类各至少 1 例；描述长度三档（≤80 / 80~400 / 400~1024）齐备；每技能资产 0 ~ 4 个（配额均值 1）且单文件落在 1 KB ~ 128 KB 幂律档；依赖出度 0 ~ 3、扇入 ≤ 2；≥ 2 个无效技能被合法技能声明为依赖；悬空依赖约占 5%；
3.1 **内核一致性锚点（实测）**：对 N=100 的夹具跑 `scanWorkspace`，无效数等于计划值、五类各自命中预期问题码（`E-FIELD-001` / `E-STATUS-001` / `E-ID-003` / `E-HASH-002` / `E-YAML-001`）、警告样本为 `ok` 且带 `W-FIELD-004`——把「无效样本真的无效」变成可证事实（F-9 的实测依据即由此固化）；
4. **不入库**：默认落系统临时目录；生成后 `git status --porcelain` 为空；`git check-ignore` 判定仓库内夹具路径被忽略（双重断言）；
5. 无效技能是**内容无效**而非结构残缺（生成器不抛错，且这些技能能被 `scan` 正常发现并在 `validate` 上报出问题）；
6. `tests/contract/bench-thresholds.test.ts` 断言需求 9.4.3 表内 N=100 / N=1000 / N=5000 三行取值与 `thresholds.mjs` 常量逐项一致（**放宽阈值会直接让契约测试变红**）；设计 2.1 的默认种子（23063 = `0x5A17`）与 92 / 8 占比同样被断言命中；
7. 既有 420 项测试不回归；新增用例全绿（用例数核对）；`check` / `typecheck` / `lint` / `format:check` 零告警。

**规模估算**：3 个脚本 + 2 个测试文件 + 1 个文档批次；不新增依赖。

**风险与处置**：Windows 落盘慢（设计 1.3 实测 N=5000 约 14 s）→ 生成阶段与测量阶段分离，生成耗时单独记录、不参与阈值判定。

### T1 测量器（RSS 采样、场景执行、固定 JSON）（实现第二批）

**执行状态**：待开始。

**目标**：把三平台 RSS 采样、握手与失败判定、场景编排与固定 JSON 输出做成可单测的模块，避免静默 0 与静默重试。

**依赖**：T0（夹具与阈值常量）。

**交付物**：

1. `scripts/bench/rss.mjs`（纯 + 执行器可注入）：三平台采样器，返回 `{ ok, mb, samples, reason }`；**采样值 0 / 空 / 读取命令失败一律判为测量失败**并给出原因；
2. `scripts/bench/measure.mjs`（纯 + 注入）：`buildMatrix()`（三档 × 四场景 × 双形态 + 每形态一次启动开销）、`sampleOnce()`（注入 spawn / 时钟 / RSS 读取器）、`summarize()`（`min` / `median` / `max` + `runs` + `exit_codes`）、`toReport()`（`schema: "bench/1"` 固定格式）；
3. `scripts/bench/profile-split.mjs`（纯）：`*.cpuprofile` → 阶段表（`readdir` / 读元文件 / YAML 解析 / 逐文件摘要 / 序列化 / 原子写 的自耗时与占比；1 ms 采样粒度，只用于占比不用于绝对值）；
4. `scripts/bench/runner.mjs`（命令行入口）：编排夹具 → 工作区 → 逐场景 spawn → 采样 → 汇总 → 落 `build/bench/*.json`；支持 `--n`、`--form source|sea|both`、`--runs`（默认 3）、`--kernel <路径>`、`--dry-run`；
5. 测试：`tests/unit/bench-rss.test.ts`、`tests/unit/bench-measure.test.ts`、`tests/unit/bench-profile-split.test.ts`、`tests/contract/bench-report.test.ts`。

**验收标准（可验证）**：

1. 三平台 RSS 解析各 ≥ 3 例（正常 / 空读 / 命令失败）；空读或 0 值必须产出**测量失败**结论（反例断言），不得记为 0 MB；
2. 矩阵完整性：场景 = `scan-cold` / `scan-hot` / `validate` / `export` 四种 × 三档 = 12，加每形态启动开销 1 项，共 13 项（断言矩阵长度与场景名集合）；
3. `--dry-run` 只打印矩阵，spawn 调用计数为 0（注入计数断言）；
4. JSON 契约：`schema` 字段、环境块、夹具摘要块、`samples[]` 字段完整；三档齐全；缺项必须带 `null` + 原因；
5. 任一非零退出码样本按**失败样本**记录（不静默重试），进程自身以非零退出码收尾；
6. 冷样本前断言索引文件不存在（F-3 前提在样本层可证）；
7. 既有测试不回归；新增全绿（用例数核对）；门禁零告警。

**规模估算**：4 个脚本 + 4 个测试文件；不新增运行时依赖（只用 Node 内置与既有 devDependencies）。

**规模估算**：1 个工作流 + 1 个契约测试增补 + 实跑记录（本地为主，CI 仅烟测）。

**风险与处置**：N=5000 在 Windows 上耗时（`scan` 单次可能数十秒）→ 该档默认 `runs` = 1，必要时手工加跑（BX-03）；本机跑测期间的干扰（其他进程负载、杀毒扫描）→ 环境块记录负载条件，异常样本按验收第 4 条复跑确认。

## 4. 硬性约束与执行纪律

1. **先文档后实现**：阈值登记（T0）先于判定实现；实现如需偏离设计，先回写设计；
2. **不新增指令**（16 条）、**不新增运行时依赖**、**不改内核行为**；压测只经既有指令入口，不得旁路写入路径；
3. **夹具不入库**，压测产物落 `build/bench/`（已在 `.gitignore` 覆盖范围内）；
4. 门禁以**退出码**判定（不以输出末行判定）；用例数核对沿用；
5. **本地优先执行**，CI 仅 `workflow_dispatch` 烟测（N=100、不上阈值）且不接入提交触发，不与 M1 门禁冲突、不占额外额度；
6. **阈值不放宽**；校准登记改前值 / 改后值 / 依据，且由契约测试钉住文档与常量的取值一致；
7. `docs/reviews/` 快照与一期 / 二期定稿不动；需求变更走变更记录批次与计数校验。

## 5. 阻塞项与需要外部条件的事项

| 编号 | 事项 | 影响 | 处置 |
|---|---|---|---|
| BX-01 | SEA 线是否支持 `--cpu-prof` / `--cpu-prof-dir`（源码线无此疑问） | 阶段耗时与索引写入延迟在 SEA 线的取法 | T2 实测；不支持则该线以 fs 观测为准并在报告标注（结论明确，不写「未验证」） |
