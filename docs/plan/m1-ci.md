## 1. 任务序列

### T1 工作流定义（实现第一批）

**目标**：落地触发策略、任务矩阵与六步验证，使推送与合并请求能自动运行且任一步失败即红。

**依赖**：设计定稿（DP-B 已定，不影响本批；DP-A 只影响夜间流水线，本批不含）。

**交付物**：工作流定义（触发事件、矩阵、步骤编排、取消旧运行的并发控制、手工触发入口）；工作流定义说明（文档级，逐条说明与本地命令的对应关系）。

**验收标准**：

1. 推送到主干与合并请求两类事件均可观测到自动运行；同一分支连续提交只保留最新运行；
2. 矩阵覆盖 Windows 与 Linux，Node 取值与版本声明同源（可核对）；
3. 六步全部经既有 npm 脚本执行，文件中不出现脚本内部的命令副本；
4. 任一步骤失败即整体失败，门禁步骤无「允许失败」设置。

**规模估算**：1 个工作流定义 + 1 份说明；不新增依赖。

### T2 缓存与产物收口（实现第二批）

**目标**：缓存生效且不改变结论，构建产物可下载并与提交对应。

**依赖**：T1。

**交付物**：依赖缓存（键含 OS、Node 版本、锁文件哈希）；产物上传（内核可执行文件与桌面构建产物，命名含平台 / 架构 / 运行标识）；失败组合诊断信息保留策略。

**验收标准**：

1. 连续两次运行中第二次出现可观测的时长下降；清空缓存后重跑结论不变；锁文件变更后缓存自动失效；缓存不可用时仍能全量通过；
2. 产物可从运行产物区下载并回溯到具体提交；失败组合的日志可获取；
3. 缓存范围不含任何宿主根路径。

**规模估算**：缓存与产物上传配置；不新增依赖。

### T3 缩减冒烟与时长收口

**目标**：按 DP-B 落实远端缩减冒烟口径，并让单次运行落在时长目标内。

**依赖**：T1（步骤编排）、T2（缓存）。

**交付物**：缩减冒烟的步骤定义（不启动 Electron，只覆盖不依赖真实窗口的部分）；运行时长实测记录与超限处置（若触及上限，按「缩减冒烟 → 拆分任务 → 缓存优化」的顺序）。

**验收标准**：

1. 流水线中不存在完整三启动方式冒烟；缩减冒烟的口径在流水线与文档中同时登记；
2. 单次运行墙钟时长在目标 ≤ 30 分钟内（硬上限 ≤ 60 分钟）；
3. 缩减冒烟本身可失败（不是空跑），且失败能定位到具体检查项。

### T4 验收与文档同步

**目标**：完成里程碑验收映射与文档刷新。

**依赖**：T1 ~ T3 + **一次真实推送或合并请求**（DP-C 的验收入口）。

**交付物**：验收映射（9.3.1 七条里程碑验收标准 → 承载任务与验证方式）；README / `docs/one-summary.md` / CHANGELOG 刷新（含 CI 运行入口与产物下载说明）；需求文档变更记录批次与计数校验。

**验收标准**：

1. 一次真实运行中六步全绿；产物可下载；失败（可刻意构造一次）能在 10 分钟内定位到具体步骤与断言；
2. 文档同步完成且「五份规范 + 五份 schema」等既有表述未被破坏；
3. 全量测试 358 项与门禁零告警（CI 接入不得改变既有测试结论）。

## 2. 依赖关系与关键路径

| 任务 | 依赖 | 说明 |
|---|---|---|
| T1 | 设计定稿 | 先文档后实现：设计文档先行，工作流文件属实现批次 |
| T2 | T1 | 缓存与产物建立在步骤编排之上 |
| T3 | T1 + T2 | 缩减冒烟与时长处置依赖缓存生效后的基线 |
| T4 | T1 ~ T3 + 真实推送 | 无真实运行即无法完成验收 |

关键路径：**T1 → T2 → T3 → T4**（T4 另需一次真实推送）。

## 3. 里程碑验收映射（需求 9.3.1 的七条标准）

| # | 验收标准 | 承载任务 | 验证方式 |
|---|---|---|---|
| 1 | 主干与合并请求两条触发路径均可自动运行 | T1 / T4 | 真实推送与合并请求各观测一次 |
| 2 | 一次提交的失败可在不登录本地环境的情况下定位到具体步骤与断言 | T1 / T4 | 刻意构造一次失败（如格式检查不通过）后核对运行记录 |
| 3 | 矩阵覆盖 Windows 与 Linux 及声明的最低 Node 版本，且与声明一致 | T1 | 矩阵取值与版本声明同源（可核对） |
| 4 | 缓存命中时长显著下降，清空缓存后结论不变 | T2 | 连续两次运行对比 + 清空缓存重跑 |
| 5 | 构建产物可从产物区下载并回溯到提交 | T2 / T4 | 下载产物并核对命名与提交对应 |
| 6 | 任一门禁步骤失败均导致失败状态，失败日志可获取 | T1 / T2 | 刻意失败 + 日志检查 |
| 7 | 接入不改变任何指令、契约与运行期行为（接入前本地全绿在接入后仍全绿） | T1 ~ T4 | 全量 358 项测试与门禁在本地与 CI 同口径通过 |

## 4. 硬性约束与执行纪律

1. **先文档后实现**：设计（本文档与设计文档）先于工作流定义；
2. **不修改一期 / 二期定稿内容与 `docs/reviews/` 快照**；需求侧如需变更走变更记录批次；
3. **四条工程约定继续适用**：用例数核对、改行为回看用例语义、选项登记一致性、含子进程的指令断言走独立进程；
4. **免费额度内运行**：不引入付费 runner；矩阵先按最小覆盖，夜间流水线默认关闭；
5. **CI 不触碰真实宿主目录、不执行被管理对象的代码、除依赖安装与产物上传外不访问外部网络**；
6. **单次运行时长目标 ≤ 30 分钟、硬上限 ≤ 60 分钟**；超限处理不得放宽门禁；
7. 工作流文件、缓存与产物配置属实现阶段产物，不在设计与计划文档中出现。

## 5. 阻塞项与需要外部条件的事项

| 编号 | 事项 | 影响 | 处置 |
|---|---|---|---|
| DP-A | 仓库可见性（公开 / 私有） | 免费额度与并发；夜间流水线是否启用 | 待确认方给出；本设计按最小覆盖推进，不受阻塞 |
| DP-C | 验收所需的真实推送 / 合并请求 | T4 无法在本地完成 | 由维护者执行或授权执行；这是唯一的验收入口 |
| CI-Q-01 | 夜间完整流水线是否启用 | 额度占用 | 默认关闭，T3 收口后按需启用（不阻塞里程碑） |
| 环境限制 | 自本环境 HTTPS 到 GitHub API 被拦（git 传输可达） | 无法从本地查询仓库可见性或运行状态 | 验收以运行记录为准；如需程序化查询，由具备网络条件的一方执行 |

## 6. 与 M2 的衔接

1. M2 在 M1 的步骤定义上**扩 OS 维度**（macOS arm64 / x64、Linux x64 的产物构建与轻量冒烟），不维护第二套步骤序列；
2. M1 上传的产物是 M2 的对照基线（Windows x64 产物沿用二期结论）；
3. M1 的缓存策略与取消旧运行机制按同样口径用于 M2 的矩阵扩展；若 macOS runner 的排队与时长成本影响门禁时长，按 DP-A 与 CI-Q-01 的额度约束处理。
