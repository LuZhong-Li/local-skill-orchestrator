## 1. 设计概述

### 1.1 目标

把既有的人工验证集合固化为每次提交自动执行的流水线：推送到主干与合并请求触发六步验证（测试 / 契约与分层校验 / 类型检查 / 代码规范 / 格式检查 / 构建），任一步骤失败即在该次提交上呈现为失败，并可下载产物 [M1-R1 ~ M1-R6]。

### 1.2 范围

| 本设计覆盖 | 不在本设计范围 |
|---|---|
| 触发策略、任务矩阵、步骤集合、缓存、产物上传、失败门禁、时长与可诊断性 | macOS runner 与跨平台产物验证（归 M2） |
| CI 环境隔离与离线约束、可观测性与审计要求 | 发布、版本号、签名与公证（不在本阶段任何里程碑） |
| 需要真实推送才能完成的验收入口 | 完整三启动方式界面冒烟（留在本地口径）[M1-R6] |

### 1.3 设计原则

1. **不在 CI 复制本地命令**：各步骤一律调用仓库既有的 npm 脚本，不把脚本内部的命令抄进流水线——否则脚本内部换实现时流水线不会跟着变，且跨 shell 的 glob 展开差异会引入假失败 [侦察 4]；
2. **版本声明单一来源**：Node 版本取自仓库的版本声明文件，不在流水线里硬编码 [M1-R2]；
3. **门禁不接受例外**：任何步骤与任何矩阵组合都不得设为允许失败 [M1-R6]；
4. **失败可诊断优先于省时长**：宁可多留日志与产物，也不减少可定位信息 [NFR-M1-01]；
5. **CI 不得触碰真实宿主目录**：M5 引入的宿主分发能力在 CI 环境中必须处于不可达状态 [侦察 5]。

## 2. 前置侦察结论（设计输入，已实测）

| # | 事实 | 证据 | 对设计的影响 |
|---|---|---|---|
| 1 | 全库**无任何 CI 配置**（`.github/`、GitLab、Azure、CircleCI、Travis 均不存在） | 目录探测 | 从零建立，不存在与既有流水线冲突的问题 |
| 2 | 远端为 `github.com/LuZhong-Li/skill-manager`，分支 `main`；`origin/main` 停在 `e67e8dd`，本会话的 22 次提交**尚未推送**；git 传输可达而 HTTPS API 自本环境被拦 | `git ls-remote --heads origin` 成功 | 验收必须包含一次真实推送/PR；**仓库可见性**决定额度与矩阵宽度（DP-A） |
| 3 | Node 版本声明三处一致：根 / 内核 / 界面 `engines.node >= 22`，`.nvmrc = 22` | 读取三个 package.json 与 `.nvmrc` | 矩阵覆盖的最低版本为 22，且须与声明同源 [M1-R2] |
| 4 | 可用的步骤命令：`npm test`（358 项）、`npm run check`（契约 + 分层）、`npm run typecheck`、`npm run lint`、`npm run format:check`（只读）、`npm run build`（内核 SEA + 桌面构建） | `package.json` 的 scripts | 六步全部有既有入口；**必须使用 `format:check`**，写入式的 `format` 不得出现在流水线 [M1-R3] |
| 5 | 测试全部使用系统临时目录，不写仓库外真实路径：宿主真实根相关用例以配置覆盖指向临时目录，`/home/u` 与 `LOCALAPPDATA` 只作为解析函数的入参 | 用例代码检索 | CI 不会触碰真实宿主目录；M5 的 `--host` 安全性质在 CI 中同样成立 |
| 6 | 界面冒烟脚本启动 Electron 并经调试协议校验，使用临时空闲端口 | 脚本代码检索 | 需要图形环境：Linux runner 需 xvfb 才能跑；据此按 DP-B 收窄远端冒烟口径 [M1-R6] |
| 7 | 打包（Installer / Portable）与构建分离，打包入口为界面工作区的独立脚本 | `package.json` 与工作区脚本 | M1 只跑构建并上传产物；**打包产物验证归 M2** |
| 8 | 远端来源相关测试用**回环 HTTP 服务 + 真实 `git` 二进制**构造，无外部网络需求 | 用例代码检索 | CI 只需 runner 自带 `git`（GitHub 托管 runner 具备）；除依赖安装与产物上传外不访问外部网络 |

## 3. 触发策略 [M1-R1]

| 事件 | 行为 |
|---|---|
| 推送到主干与长期维护分支 | 自动触发 |
| 合并请求（打开、提交同步、重新打开） | 自动触发 |
| 同一分支的连续提交 | 取消仍在进行的旧运行，结论只以最新提交为准 |
| 手工触发 | 提供入口，用于复现问题与排查，步骤集合与自动触发一致 |
| 夜间完整流水线（可选） | 承载长耗时检查；不属每次提交的门禁，失败不改变提交状态，但同样保留日志与结论 |

设计要点：

1. 取消旧运行是**额度纪律**而非优化：同一分支排队多个运行既浪费额度，也让「哪个运行代表当前结论」变得含糊；
2. 文档与说明类改动是否触发完整矩阵由实现阶段决定；**若做路径过滤，必须保证门禁步骤在全量触发时不被跳过**（过滤只允许跳过，不允许改变步骤语义）；
3. 夜间流水线默认**关闭**，仅在需要长耗时检查时才启用（DP-A 与额度相关）。

## 4. 任务矩阵 [M1-R2]

| 维度 | 取值 | 说明 |
|---|---|---|
| 操作系统 | `windows-latest`、`ubuntu-latest` | macOS 归 M2；矩阵先覆盖两个 OS 以控制额度 |
| Node 版本 | **最低支持版本（22）**，取自版本声明文件 | 不在流水线里硬编码；版本声明变更时矩阵自动跟随 |
| 组合数 | 2 × 1 = 2 | 每个组合独立运行、独立呈现结果 |

设计要点：

1. **同源性**：矩阵的 Node 取值以 `.nvmrc` 为准（单一来源），因此「矩阵覆盖的最低支持版本与声明一致」是结构性成立而非靠人工核对 [M1-R2 验收 2]；
2. 若未来纳入更高 Node 版本或其他 OS，必须与既有组合同为门禁；**实验性组合必须显式登记为非门禁组合并说明理由**，不得默认允许失败 [M1-R6]；
3. 不为 macOS 建立独立流水线：M2 在 M1 的步骤定义上扩 OS 维度，不维护第二套步骤序列。

## 5. 步骤定义 [M1-R3]

顺序与依赖（单次运行内的阶段划分，具体任务编排属实现阶段）：

| 序 | 步骤 | 调用 | 说明 |
|---|---|---|---|
| 0 | 依赖安装 | 依赖安装命令（按锁文件） | 缓存命中时快速完成；失败即整体失败 |
| 1 | 契约校验与分层校验 | `npm run check` | 契约（指令清单 / 结果封装 / 退出码 / schema 字段一致性）与分层约束 |
| 2 | 类型检查 | `npm run typecheck` | 内核与界面两侧 |
| 3 | 代码规范 | `npm run lint` | — |
| 4 | 格式检查 | `npm run format:check` | **只读检查**；不得使用写入模式 |
| 5 | 测试 | `npm test` | 单元 / 契约 / 端到端，含实际执行用例数核对 |
| 6 | 构建 | `npm run build` | 内核独立可执行文件 + 桌面构建 |
| 7 | 缩减冒烟 | 按 DP-B 的口径执行 | 见下 |

设计要点：

1. **步骤与本地命令一一对应**：流水线只调用 npm 脚本，不复制内部命令 [M1-R3 验收 3]；
2. **用例数核对**：测试步骤必须核对实际执行的用例数与声明一致（工程约定第一条）——「无失败」不等于「全跑过」；
3. **含子进程的断言走独立进程**（工程约定第四条）在 CI 与本地同口径，不由 CI 改变；
4. **缩减冒烟口径（DP-B，已定）**：远端**不启动 Electron，也不跑三启动方式**；缩减冒烟只覆盖不依赖真实窗口的部分（构建产物存在性与内核侧可执行性检查）。完整三启动方式冒烟继续在本地执行，其归属在流水线与文档中同时登记 [M1-R6]。

## 6. 缓存策略 [M1-R4]

| 缓存对象 | 键 | 说明 |
|---|---|---|
| 依赖缓存（包管理器缓存目录） | 操作系统 + Node 版本 + 依赖锁文件哈希 | 跨运行复用；不同 OS 与 Node 不互相污染 |
| 构建中间产物 | —（**不缓存**） | 内核以单文件可执行形态产出（含运行时副本），跨运行缓存收益低且易与源码不同步，故不缓存 |

设计要点：

1. **缓存只影响时长，不影响结论**：命中与未命中必须产生相同结论；缓存不可用时流水线退化为全量执行并仍可通过 [M1-R4 验收 2、4]；
2. **缓存失效不得导致步骤被跳过**：缓存只决定「是否重新下载依赖」，不决定「是否执行某步骤」；
3. 锁文件变更后缓存自动失效（键含锁文件哈希）[M1-R4 验收 3]；
4. 缓存**不缓存用户目录中的宿主目录**：任何缓存范围都不得包含 M5 的宿主根路径 [侦察 5]。

## 7. 产物上传 [M1-R5]

| 产物 | 内容 | 命名要求 |
|---|---|---|
| 内核可执行文件 | 构建产出的内核单文件 | 含平台、架构与运行标识 |
| 桌面构建产物 | 桌面外壳的构建输出目录 | 同上 |
| 失败组合的日志与上下文 | 由运行记录承载；失败时不得因「只上传成功产物」而丢失诊断信息 | 与提交对应 |

设计要点：

1. 产物用于 M2 的跨平台对照与人工下载验收，因此命名必须可与提交对应 [M1-R5 验收 1]；
2. 上传范围覆盖通过门禁的组合；**失败组合的诊断信息同样必须保留**；
3. 产物不得包含敏感配置与证书（本阶段无凭据类产物；若未来引入，按 9.6.2 凭证约束处理）。

## 8. 失败门禁、时长与可诊断性 [M1-R6、NFR-M1-01]

1. **门禁**：任一步骤失败即整体失败；矩阵中任一组合失败即失败；门禁步骤不得设为「允许失败」「忽略错误」或以其他方式吞掉失败；
2. **时长**：单次运行墙钟时长目标 ≤ 30 分钟、**硬上限 ≤ 60 分钟**；触及上限按「缩减冒烟 → 拆分任务 → 缓存优化」的顺序处理，**不得放宽门禁** [NFR-M1-01]；
3. **可诊断**：失败必须在 10 分钟内定位到具体步骤与具体断言——由步骤级结果、原始输出与失败摘要三者共同保证 [NFR-M1-01]；
4. **可追溯**：每次运行必须能关联到具体提交、矩阵组合与产物 [NFR-M1-01、9.4.6]。

## 9. 环境隔离、安全与离线约束

1. **不触碰真实宿主目录**：CI 环境不得存在真实宿主根（如用户主目录下的宿主技能目录），测试与脚本一律通过配置覆盖使用临时目录 [侦察 5]；
2. **不执行被管理对象的代码**：CI 不得执行任何被管理 Skill 内的脚本或可执行文件 [需求 9.6.2]；
3. **网络**：除依赖安装与产物上传外不访问外部网络；远端来源测试使用回环地址，不需要外网 [侦察 8]；
4. **不采集遥测**：CI 不上传任何使用数据 [需求 NFR-06]；
5. **依赖不新增**：CI 不得引入新的运行时依赖（runner 自带的 `git` 除外，属平台能力）[需求 9.6.2 依赖约束]。

---

## 10. 可观测性与审计 [9.4.6、9.7]

1. 每次运行产出：运行记录与原始日志、失败摘要、产物；夜间流水线同样产出并保留；
2. 每份产物注明「自动校验 / 人工校验 / 宿主侧确认」的来源（9.4.6 第 3 条），M1 范围内全部为自动校验；
3. 交付物按 9.7 的 M1 行提交：工作流定义说明（文档级）、运行成功的日志与合并请求示例、产物下载入口、故障复现日志样例。

## 13. 边界与排除项

1. 本文档不含工作流文件、缓存配置或任何 CI 配置——均属实现阶段产物；
2. 不含 macOS / Linux 打包与产物验证（归 M2）、发布与签名、变更日志生成、部署；
3. 不改变任何既有指令语义与测试结论：接入 CI 不得要求修改既有用例语义（若必须修改，按「改行为回看用例语义」约定登记）；
4. 不在 CI 中引入付费 runner 或付费服务。
