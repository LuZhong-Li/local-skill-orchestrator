## 1. 调研结论（前置实测，2026-10-16）

### 1.1 跨平台峰值内存测量

**选定方法**：父进程 spawn 内核子进程，**子进程分配完成后经 stdout 送出就绪信号并阻塞在 stdin**，父进程在子进程存活期内连续采样三次取最大；各平台读取口径如下。

| 平台 | 采样口径 | 精度特征 |
|---|---|---|
| Linux | `/proc/<pid>/status` 的 `VmHWM` | 内核维护的**峰值**，单次读取即准确 [已查证·实测] |
| macOS | `ps -o rss= -p <pid>` | 瞬时 RSS，需重采样取最大（近似峰值）[已查证·实测] |
| Windows | PowerShell `(Get-Process -Id <pid>).PeakWorkingSet64` | 系统维护的**峰值**，单次读取即准确 [已查证·实测] |

**四环境实测**（同一个「分配 192 MB 后驻留」的子进程；括号内为采样值）：

| 环境 | 峰值 | 结论 |
|---|---|---|
| ubuntu-24.04 runner (x64) | **238 MB**（244148 KB ×3） | 与分配量之差 ≈ 46 MB＝Node 运行时基线 |
| macos-15 runner (arm64) | **231 MB**（236640 KB ×3） | 差异 ≈ 39 MB |
| windows-latest runner (x64) | **224 MB**（229280 KB ×3） | 差异 ≈ 32 MB |
| 本机 Windows (Node 24.14.1) | **228 MB**（233324 KB ×3） | 差异 ≈ 36 MB |

**结论**：三平台各有可用口径，四环境偏差一致（32 ~ 46 MB），**可作为同一量纲横向比较** ✓。

**实测踩到的两个坑（已写入测量器设计）**：

1. **退出竞态**：无就绪握手时，父进程定时采样可能落在子进程退出之后——Linux 上读 `/proc/<pid>/status` 直接 `ENOENT` 抛错（实测使 Linux leg 整体失败），macOS/Windows 的 `ps` / PowerShell 只是返回空值而**静默记成 0**（实测 Windows runner 报 `峰值 0 MB`）。共同解法是**握手 + 存活期采样 + 采样异常容错**。
2. **静默零值**：Windows runner 首版探针返回 0 MB 而不报错——测量器必须把「采样值 0 / 空」视为**测量失败**，而不是「内存很小」。

### 1.2 测量口径

| 问题 | 调研结论（依据：内核实现 + 实测） |
|---|---|
| 冷热两态 | **冷**＝无索引（`init` 后立即测 `scan`，含首次发现与元文件解析）；**热**＝索引已存在（再次 `scan`、`validate`、`export`）。两态都要记录 [设计约定] |
| 墙钟是否含进程启动 | **含**：墙钟按「spawn → 子进程退出」计（`process.hrtime.bigint()` 外层），与工程约定④ 一致；同时**单列启动开销**，便于区分固定成本与规模成本（实测见 1.4） |
| `scan` 与 `validate` 的区别 | `scanWorkspace` 走 `readdirSync` + `readFileSync` + `parseYaml`（**同步、单线程、逐文件解析**，`kernel/core/discovery/index.ts`）；`validateWorkspace` 只读**已加载的索引** + `statSync` 目录探测、**不重新解析全部元文件**（`kernel/core/validation/index.ts` 无 `readFileSync`）→ 两者成本模型不同，必须分别建模 [已查证·源码] |
| `export` 的 IO 占比 | `exportIndex` 在内存组装整份文档后 `stringifyYaml(document)` 再 `atomicWriteFile`（`kernel/core/backup/index.ts:238`）→ **全量内存缓冲 + 单次原子写**，IO 占比取决于索引体积而非资产体积 [已查证·源码]；导出体积与「逐文件摘要」增量在 M3-R2 一并记录 |
| 并发模式 | 内核当前为**全同步单线程**（无 worker）；M3-R2 的「单线程 / 多线程对比」在现状下等价于「现状基线 + 未来优化对照位」，设计取：先测现状基线，多线程作为**观察位**（若实现批次引入 worker 再补测）[设计约定，与 9.3.3「仅观察、不作架构改造」一致] |

### 1.3 夹具规模实测

同一生成器（`skills/<id>/{skill_meta.yaml, SKILL.md, assets/blob.bin}`）四环境实测：

| 环境 | N=1000 生成耗时 | N=5000 生成耗时 | 文件数 / 体积 |
|---|---|---|---|
| ubuntu-24.04 | **150 ms** | **1265 ms** | 3000 / 15000 个文件；32 MB / 160 MB |
| macos-15 | **321 ms** | **2602 ms** | 同上 |
| windows-latest | **3947 ms** | **13772 ms** | 同上 |
| 本机 Windows | 3384 ms | 16924 ms | 同上 |

**结论**：两档夹具在任何环境都可实测内生成（最慢的 Windows runner 上 N=5000 约 14 s），**不必入库夹具**；N=5000 的 160 MB 规模在临时目录可承受 ✓。

### 1.4 发布二进制 vs 源码运行的启动开销

「`<内核> --version`」与「`node kernel/entry/cli.ts --version`」各 5 次取中位（含进程启动）：

| 环境 | 源码 node | SEA 单文件 | 结论 |
|---|---|---|---|
| ubuntu-24.04 | 184 ms | **47 ms** | SEA 快约 4× |
| macos-15 | 151 ms | **13 ms** | SEA 快约 12× |
| windows-latest | 327 ms | **96 ms** | SEA 快约 3.4× |
| 本机 Windows | 171 ms | **59 ms** | SEA 快约 2.9× |

**结论**：发布二进制**不仅不慢，启动还显著更短**（源码路径要额外做类型剥离与模块加载）。因此双线口径为：**发布二进制线测「用户实际拿到的形态」**，源码线用于对比固定成本与定位实现层瓶颈；两线都要记录，且**不混用同一阈值口径**（差异主要是固定启动项）。

### 1.5 CI runner 规格与波动（不设阈值门禁的依据）

GitHub 官方 runner 表（2026-10-16 读取）：公共仓库的标准 runner 免费且不限量；`ubuntu-24.04` 与 `windows-latest` 为 4 vCPU / 16 GB / 14 GB SSD；`macos-15`（arm64）为 3 vCPU / 7 GB / 14 GB SSD。

**为何 CI 不做阈值门禁**：

1. runner 是**共享硬件池**，官方只承诺 vCPU / 内存规格，不承诺 I/O 与单核性能稳定性；
2. 实测已见波动：同一探针跨两次运行，macOS 的 N=5000 夹具生成 3144 ms → 2602 ms（≈ 17%）、Windows 14460 ms → 13772 ms；启动开销同样在 ±30% 量级抖动；
3. 因此 CI 只做 **N=100 烟测 + 数据记录（不上阈值）**；**阈值判定放在本机固定环境**（同硬件、同 Node、同夹具、同机时），并保留**同机重复测量的波动带**作为回归判定依据 [设计约定，与裁决 4 一致]。

## 2. 夹具生成器设计（`scripts/bench/fixture.mjs`）

### 2.1 分布参数（可复现的「真实分布」）

固定种子（默认 `0x5A17`，CLI 可覆盖）驱动 `mulberry32` 伪随机序列，逐技能生成：

| 维度 | 分布 | 目的 |
|---|---|---|
| 合法 / 无效占比 | 默认 92% 合法、8% 无效（四类：缺必填字段、未知字段、版本非法、资产缺失声明） | 覆盖校验路径与错误报告成本（M3-R2 要求无效技能占比可复现） |
| 描述长度 | 短（≤ 80 字符）40%、中（80~400）45%、长（400~1024）15% | 触发描述长度上限与截断相关路径 |
| 资产规模 | 每技能 0~4 个资产，单文件 1 KB ~ 256 KB 幂律（`size = 1KB × 2^floor(u×8)`） | 让导出与索引摘要成本随资产规模变化 |
| 依赖深度 | 链式深 0~3、扇出 0~2 | 覆盖依赖检查的图遍历成本 |
| 元文件形态 | `skill_meta.yaml` + `SKILL.md`（frontmatter）+ `assets/` | 与真实工作区布局一致（沿用既有测试夹具形态） |

### 2.2 目录布局与不入库

```
<夹具根>/skills/<skill-id>/
  ├── skill_meta.yaml     # 内部元数据（schema_version / id / version / status / source / targets / 时间戳）
  ├── SKILL.md            # frontmatter + 正文
  └── assets/blob-<n>.bin # 按 2.1 分布生成
```

夹具根由 `--root` 指定，默认落在系统临时目录；**不入库**（`.gitignore` 已覆盖 `build/`，夹具默认放临时目录；另加断言：`git status` 不得出现夹具路径）✓ 与裁决 5 一致。**可复现性**：同种子 + 同参数 → 逐文件同内容（只用确定性 PRNG，不引入时间戳随机量）。

## 3. 测量器设计（`scripts/bench/measure.mjs`）

### 3.1 指标

| 指标 | 取法 |
|---|---|
| 墙钟（端到端） | `process.hrtime.bigint()` 外层计时，覆盖 spawn → 退出 |
| 启动开销（固定成本） | 单独测 `<内核> --version`，用于拆分固定项与规模项 |
| 峰值 RSS | 1.1 的握手 + 存活期采样（三平台各自口径）；**采样失败即报错**，不用 0 兜底 |
| CPU 时间 | 跨进程拿不到时**显式记 `null`**（POSIX 的 `/usr/bin/time` 不可移植、macOS BSD `time` 无 `-v`），不伪造 |
| 索引体积 | 测量前后递归求和 `<工作区>/index/` 字节数 + 单技能平均 |
| 导出体积 | 导出文件字节数 + 单技能平均 |
| 逐文件摘要成本 | 由「冷热 scan 差值」与「索引体积 / 技能数」共同刻画（`scan` 是摘要写入路径） |

### 3.2 冷热两态与命令固定

- 冷：`mkdtemp` 新工作区 → `init` → `scan`（计时）→ `list --json`（不计时，仅确认规模）；
- 热：同一工作区再跑 `scan`、`validate`、`export --to bench-export.yaml`（各自计时）；
- 命令一律 spawn **独立进程**（工程约定④），stdout / stderr 落文件备查；**任何非 0 退出码记为失败样本**，不静默重试。

### 3.3 输出 JSON（固定格式，供基线与回归）

```json
{
  "schema": "bench/1",
  "generated_at": "2026-10-16T00:00:00Z",
  "environment": {
    "platform": "win32",
    "arch": "x64",
    "node": "v24.14.1",
    "kernel": "0.1.0",
    "kernel_form": "sea"
  },
  "fixture": { "seed": 23063, "n": 1000, "files": 3000, "bytes": 33554432, "generation_ms": 3384 },
  "samples": [
    {
      "scenario": "scan-cold",
      "n": 1000,
      "runs": 3,
      "wall_ms": { "min": 0, "median": 0, "max": 0 },
      "peak_rss_mb": { "min": 0, "median": 0, "max": 0 },
      "index_bytes": 0,
      "export_bytes": null,
      "startup_ms": 59,
      "exit_codes": [0, 0, 0]
    }
  ]
}
```

数值仅为格式示例；`runs` 默认 3 次取中位与极值，可 `--runs 1` 快速预演。

## 4. 场景矩阵

三指令 × 三档 × 冷热（`runs` = 3，取中位与极值）：

| 场景 | N=100（烟测档） | N=1000（阈值档） | N=5000（压力档） |
|---|---|---|---|
| `scan` 冷 | 必测 | 必测（阈值判定） | 必测（记录） |
| `scan` 热 | 必测 | 必测（阈值判定） | 必测（记录） |
| `validate` | 必测 | 必测（阈值判定） | 必测（记录） |
| `export` | 必测 | 必测（阈值判定） | 必测（记录） |
| 启动开销 | 必测 | 必测 | 必测（与 N 无关，随档记录便于同批对照） |
| 索引体积 / 单技能平均 | 必测 | 必测 | 必测 |

**明确不测**：GUI 交互（属 M2 本地口径）、宿主分发落位（属 M5）、网络与 registry 交互（默认离线）。**观察位（不设阈值）**：单线程 / 多线程对照（现状为全同步单线程，见 1.2）；若实现批次引入 worker，再补测并发 `scan`。

## 5. 执行策略

| 线 | 触发 | 内容 | 阈值 |
|---|---|---|---|
| 本机基线（主判定线） | `npm run bench -- --n 1000 --form both`（人工） | 三档 × 三指令 × 冷热 + 双形态；固定机时、开机后尽快跑 | **N=1000 硬阈值判定**；N=5000 只记录 |
| 发布二进制线 | 同上 `--form sea --kernel <路径>`（默认取 `build/kernel/skill-manager.exe`，可指向 `v0.1.0` Release 解包产物） | 用户实际拿到的形态 | 同上（与源码线**分开报告**，不混用口径） |
| CI 烟测 | `workflow_dispatch`（手动）+ 可选定期 | **仅 N=100** 的三个场景 + 启动开销；数据以注解与 artifact 记录 | **不上阈值**（裁决 4；依据见 1.5） |

阈值口径（需求 9.4.3 为基线；M3 前置裁决另行收紧，属 9.4.3 允许的校准方向，按「改前值 → 改后值 → 依据」登记）：

| 指标 | 9.4.3 初步阈值（N=1000） | 本设计的 M3 硬阈值（收紧后） | 依据 |
|---|---|---|---|
| `scan` | ≤ 60 s | **≤ 30 s** | 本地同步 IO + 单进程解析；1.3 的夹具规模与 1.4 的启动开销表明规模项占主导而固定项极小 |
| `validate` | ≤ 120 s | **≤ 30 s** | `validate` 不重解析元文件（1.2），成本低于 `scan` |
| `export` | ≤ 30 s | **≤ 15 s** | 全量内存组装 + 单次原子写（1.2），无逐资产 IO |
| 峰值 RSS | ≤ 1.5 GB | **≤ 512 MB** | 单进程流式处理；索引体积为 MB 量级 |
| 索引体积 | 与基线偏差 ≤ 50% | 沿用（基线取 0.1.0 实测） | 9.4.3 基线项 |

**登记说明**：上表「改后值」为 M3 前置裁决给出的硬阈值；若 T2 实测基线显示某项**已接近**收紧后的阈值，必须按 9.4.3 的拐点规则登记优化项，而**不得**把阈值放宽回 9.4.3 的初步值。

## 6. 基线与回归

1. **基线入库**：`docs/benchmark/baseline-0.1.0.json`（格式见 3.3，附环境说明）；人读报告 `docs/benchmark/report-0.1.0.md`（表格 + 拐点判定 + 结论 + 遗留项）。
2. **回归判定**：
   - **阈值档**（N=1000）：任一指标准超硬阈值即判不达标 → 按第 7 章预案定位瓶颈，**不放宽阈值**；
   - **同机波动带**：以基线记录的 `min / median / max` 为带；超出 `max × 1.5` 视为显著回归候选；
   - **显著回归告警**：候选须在**同一环境重跑一次**确认（排除单次抖动，依据 1.5 的实测波动）；确认后登记为优化项并计入实现批次。
3. **可比性约束**：不同平台 / runner 的绝对值**不做横向阈值比较**，只做同环境时序对比；跨环境只比较「量级与拐点」。
4. **拐点判定**（需求 9.4.3）：单技能平均耗时、单技能平均内存、索引写入延迟三项在相邻规模（100 → 1000、1000 → 5000）增长 > 2× 即触发优化项登记；本设计的测量器已按单技能平均口径输出，可直接参与判定。

## 7. 瓶颈预案（若 N=1000 不达标）

按「先定位、再优化、阈值不动」的顺序处理；候选路径与优先级（依据 1.2 的实现事实）：

| 优先级 | 候选优化 | 依据与预期 |
|---|---|---|
| 1 | **扫描的 IO 批量化**：把逐文件 `readFileSync` + `parseYaml` 改为受限并发（`fs/promises` + 并发上限） | `scanWorkspace` 目前全同步串行（1.2），并发化对 N 档收益最直接；须保持结果确定性 |
| 2 | **元文件解析前置校验**：先用廉价的头部扫描筛掉明显无效技能，再解析完整 frontmatter | 夹具含 8% 无效技能，错误路径不应触发全量解析 |
| 3 | **导出流式化**：`exportIndex` 由「内存组装 + `stringifyYaml`」改为流式写出（分块序列化 + 顺序写） | 直接改善峰值 RSS 与导出墙钟（1.2），也是 512 MB 阈值的主要保障 |
| 4 | **索引写入批量化**：索引写入从「逐次写」改为批量提交（若实测显示写入延迟主导） | 对应 M3-R2 的「索引写入延迟」指标 |
| 5 | **内存不落全量资产**：确保任何路径都不把资产内容读进内存（当前导出只涉及索引文档，但要防回归） | 保障 RSS 与资产规模解耦 |

**边界**：以上均为**候选**，是否实施取决于 T2 实测的瓶颈定位；实施须另立实现批次（含用例与回归对比），不得在本设计或测量器中顺带改动内核行为。

## 8. 开放决策点

| # | 决策点 | 现状 | 影响 |
|---|---|---|---|
| ① | 阈值收紧的最终口径 | 9.4.3 初步值 vs 裁决收紧值（本设计取后者） | 若认为收紧过早，可按 9.4.3 的校准流程回退为「先按初步值判定，实测后再收紧」 |
| ② | 多线程 / worker 对照的落地形态 | 现状全同步单线程，仅登记为观察位 | 若要求真实并发对照，需先做一次架构层评估（超出 9.3.3「不作架构改造」的边界） |
| ③ | N=5000 是否纳入定期执行 | 本设计仅作记录档、人工触发 | CI 额度与时长（单档预计数分钟）；若纳入，需按 9.4.1 的时长上限评估 |
| ④ | 基线是否随每个版本重录 | 本设计以 0.1.0 为基线 | 版本迭代后的基线漂移判定口径 |
| ⑤ | 夹具分布是否需要在首个基线后校准 | 2.1 的分布为设计取值 | 若实测显示某维度不敏感，可简化夹具（须登记变更与依据） |
