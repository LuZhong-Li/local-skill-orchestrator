## 0. 范围裁定（先取证，再设计）

需求 9.3.4 对 M4a 的定义是**Skill 的更新检查**，不是应用自更新：

> 「自动更新」在本阶段被定义为**新版本检查与提示**：按用户要求检查**登记来源**是否存在更新的版本，并把可更新项呈现给用户。
> 检查源必须显式定义并**限定为已登记来源（索引中的来源信息）**，不得引入独立的远端清单服务。（M4a-R2）
> `update` 的既有语法、参数、行为与输出契约**不变**；本项是对其**消费端**的扩展。（M4a-R5）

**因此**：`electron-updater` / Squirrel / `latest*.yml` / 平台安装包形态这些**属于应用自更新**，不属于 M4a。它们与 M4a 的四条边界（检查只读、执行复用 `update`、不新增指令、未签名现状）在语义上互斥——应用自更新无法「复用 `update` 指令」，也无法用「登记来源」作为检查源。

**应用自更新**：本设计给出取证与结论（第 2.1 节），但**建议单独立项**（需先有签名与更新元数据），不在 M4a 内实现。

## 1. 现状取证（仓库内）

### 1.1 `update` 指令的语义与能力边界

| 项 | 现状 | 位置 |
|---|---|---|
| 更新对象 | **已安装的 Skill**（不是工具自身）：刷新记录投影与派生区、重分发既有副本 | `cli-contract.md` 4.11；`kernel/core/lifecycle/index.ts` `updateSkill` |
| 本地来源 | 重新获取并替换中心库原件 | 同上（`refetchable` 为 git/archive 且声明了 `location`） |
| **远端来源** | **可重新获取**：`readDeclaredSource` 把 `source.url` 折入 `location`，`acquireSource` 按 `looksRemote()` 走克隆/下载；远端与本地共用同一 refetch 路径 | `kernel/core/lifecycle/source.ts`；T0 回环 `git daemon` 实测 |
| 契约原文 | 远端来源（`url` + `ref`）与本地来源走同一套重新获取路径；本地来源的语法、参数、行为、输出载荷与退出码保持不变 | `cli-contract.md` 4.11（T0 纠偏） |
| `--check` | 只检查并报告**本地漂移与版本差异**，不写盘 | 同上 |
| 显式触发 | **「更新只能由用户显式发起，不得在后台自动执行。自动更新与后台升级不属于本规范范围。」** | `cli-contract.md` 4.11「显式触发约束」 |
| 退出码 | 来源不可解析 4；依赖未满足 6 | 同上 |

**F1 已关闭（T0 实测更正）**：远端 refetch 在 M4a 之前已经实现，缺口在契约文本与测试覆盖，不在能力本身。T0 已纠正 `cli-contract.md` 4.11、更正过期注释，并用回环 `git daemon` 验证「远端推进 → `update` → 内容与指纹同时更新」。因此 M4a 的「检查 → 确认 → `update`」链路对远端标签型 git 来源可达。

### 1.2 既有网络与错误口径（新能力必须沿用）

| 项 | 现状 |
|---|---|
| 远端获取实现 | `kernel/core/lifecycle/source.ts`：git `clone --quiet`（可带 ref）、`fetch` + 归档解压（zip/tar）、大小上限与超时 |
| 超时 | `REMOTE_TIMEOUT_MS` 默认 **60 000 ms**（可用 `SKILL_MANAGER_SOURCE_TIMEOUT_MS` 覆盖）[已查证·源码] |
| 体积上限 | `REMOTE_MAX_BYTES` 默认 **128 MiB** [已查证·源码] |
| 问题码 | `E-SRC-001` 不可解析、`E-SRC-002` 远端失败、`E-SRC-003` 获取失败、`E-SRC-004` 不安全归档、`E-SRC-005` 命令不可用、`E-SRC-006` 超时、`E-SRC-007` 下载失败、`E-SRC-008` 超限、`E-SRC-009` 协议被拒、`E-SRC-010` 需要认证 |
| 认证/限流映射 | HTTP 401/403 → `E-SRC-010`（需要认证）；其余非 2xx → `E-SRC-007` [已查证·源码] |

**设计约束**：M4a 的检查沿用同一批问题码与同一套超时/上限口径，**不新增错误风格**。

### 1.3 内核 SEA 与 GUI 的更新边界

| 形态 | 内核位置 | 更新方式 |
|---|---|---|
| 桌面应用（GUI） | `resources/kernel/`（随 app 分发） | 内核随 app 一起更新；单独替换内核会与界面契约错配 |
| 纯 CLI（SEA 单文件） | 用户自选路径 | **自更新不在 M4a**：Windows 上运行中的可执行文件无法就地覆盖（需改名/重启辅助），且无签名校验链；属应用自更新问题 |

**结论**：M4a 的检查与执行都只针对 **Skill**，与内核自身版本无关。

### 1.4 发布物现状（应用自更新的可行性证据）

|---|---|

## 2. 外部调研（官方证据）

### 2.1 应用自更新（`electron-updater` / Squirrel）——**不属于 M4a，仅给出结论依据**

| 平台 | 机制与签名要求 | 本项目结论 |
|---|---|---|
| macOS | electron-updater 使用 **Squirrel.Mac**；Squirrel.Mac 对下载到的更新包执行「**与解包 ZIP 相同的代码签名校验**」（官方 README 原文：*puts the result through the same code signing verification as an unpacked ZIP*）[已查证] | **降级为打开 Release 页引导**：本项目未签名/无公证，且未发布 `latest-mac.yml`，两条都不满足 |
| Windows（NSIS） | 更新通过 `latest.yml` 获取元数据；`publisherName` / 强校验只在配置时生效 [待确认：具体键语义需在实现批次核对官方手册] | **降级引导**：未发布 `latest.yml` |
| Linux（AppImage） | AppImage 更新要求运行体是 AppImage 且文件可写；`--appimage-extract-and-run` 是解包运行、不具备可更新形态 [待确认：实现批次实测 `APPIMAGE` 环境变量] | **降级引导**：未发布 `latest-linux.yml` |
| portable.exe | 便携单文件是自解压运行形态，无安装位置与更新元数据 [待确认：实现批次核对 electron-builder 文档] | **降级引导** |

> 该矩阵的用途：若未来要做「应用自更新」，必须先满足 **签名 + 发布 `latest*.yml`** 两个前提；在那之前，所有平台的结论都是「打开 Release 页」。这也是为什么它不属于 M4a——M4a 的四条边界（检查只读、复用 `update`、不新增指令、未签名）无法容纳它。

### 2.2 GitHub Releases 只读检查通道（未来应用自更新的数据源）

| 项 | 证据 |
|---|---|
| 未认证 REST 限流 | **60 请求/小时/IP**（官方文档原文：*The primary rate limit for unauthenticated requests is 60 requests per hour.*）[已查证] |
| 认证限流 | 5 000 请求/小时 [已查证] |
| `prerelease` 语义 | `/releases/latest` 排除 prerelease 与 draft ✓（本项目 v0.1.2 实测 `latest=v0.1.2`）[已查证·实测] |

**注意**：M4a 的检查源是**已登记来源**（M4a-R2 明令不得引入独立清单服务），因此**不**使用 GitHub Releases 通道；该证据仅用于第 2.1 节与未来立项。

### 2.3 远端来源的只读检查（M4a 真正需要的）

| 项 | 证据 | 用途 |
|---|---|---|
| `git ls-remote` | 官方文档：*Displays references available in a remote repository along with the associated commit IDs.* [已查证] | git 来源的**只读**检查：解析 `ref` → 远端 commit；列 `--tags` 取标签集合 |
| semver 优先级 | 主版本.次版本.修订号比较；**prerelease 低于同版本正式版**（semver.org 2.0.0 第 11 条）[已查证] | 标签型来源的「是否有更新」判定 |
| 归档来源 | 无版本标识；只能取 HEAD（状态/长度/ETag/Last-Modified） | 仅能报「可下载性」，不能判定「更新」 |

## 3. 设计

### 3.1 检查能力（只读）——承载位置与结果形状

**承载位置（推荐：GUI 主进程）**：

- `update` 的契约被 M4a-R5 冻结（语法/参数/行为/输出不变），任何「给 `update` 加远端检查」的方案都与之冲突；
- 检查是**消费端能力**（R5 原文「本项是对其消费端的扩展」），放在 GUI 主进程不触碰任何 CLI 契约；
- 执行阶段仍调用既有 `update` 指令（第 3.3 节），不另起写入流程。

**备选**：在 `list` / `inspect` 上新增选项（需契约变更）。**不建议**：M4a 明令不新增指令，而给既有指令加网络行为会改变其语义边界（`list` 变慢、失败语义复杂）。

**结果形状**（沿用结果封装的字段风格与问题码，GUI 内部结构化）：

```json
{
  "command": "update-check",
  "ok": true,
  "findings": [{ "code": "E-SRC-006", "severity": "warning", "target": "skill-id", "message": "…" }],
  "data": {
    "checked_at": "2026-10-17T00:00:00Z",
    "items": [
      {
        "id": "code-review",
        "state": "update-available",
        "installed_version": "1.2.0",
        "available": { "ref": "v1.3.0", "commit": "…" },
        "provenance": { "url": "https://…", "ref": "v1.2.0", "checked_at": "…" },
        "summary": "来源标签 v1.3.0 高于已安装版本 1.2.0",
        "backup_notice": "执行前将先行备份"
      }
    ]
  }
}
```

**四态判定表**（M4a-R3 要求的四种状态，全部可达；T1 实现的规范名称如下）：

| 来源形态 | 判定 | 依据 |
|---|---|---|
| 远端 git，`ref` 为 **semver 正式版标签**（如 `v1.2.0`） | 列远端标签 → 取最高正式版 → 与基线比较 → `update-available` / `up-to-date` | semver 比较 [已查证] |
| 远端 git，`ref` 为**分支/提交/预发布或非 semver 标签** | `not-checkable`，原因区分引用形态 | 缺少可比较的正式版基线 |
| 远端归档（url） | `not-checkable`（原因：归档无版本标识；仅报告 HEAD 可下载性） | 第 2.3 节 |
| 本地来源（`location`） | `not-checkable`（原因：本地来源无「新版本」概念；本地漂移由 `update --check` 覆盖，提示用户改用 CLI） | 契约 4.11 |
| 来源缺失或 `unknown` | `not-checkable`（M4a-R2 要求显式标记） | 需求 M4a-R2 |
| 网络/限流/认证失败 | `failed`（带 `E-SRC-*` 问题码与可读说明） | 第 1.2 节 |

> **限制要写在产品文案里**：当前只有「标签型 git 来源」能给出 `update-available`；分支与归档需要「记录已安装引用」这条派生字段（见已裁决事项 ④）。

**T1 比较规则（实现前定死）**：

1. 只有远端 git + `ref` 为 semver 正式版标签才进入远端探测；`v1.2.0` 与 `1.2.0` 归一为同一基线；
2. 远端只比较正式版，排除 prerelease（如 `v1.3.0-rc.1`）与非 semver 标签（如 `latest`、`feature-x`）；
3. 基线优先取来源 `ref` 的正式版标签；没有可用的 `ref` 时回退到元文件 `version`；
4. 远端最高正式版高于基线 → `update-available`；相同或更低 → `up-to-date`；
5. 基线来自 `ref` 标签、但远端已不存在该标签（删除或 force-push）时，判 `not-checkable` + `baseline-tag-missing`：远端列表本身可读，不应伪造 `E-SRC-*` 网络失败，也不能在缺少基线的情况下猜「可更新」；
6. `annotated tag` 的 peeled 引用（`refs/tags/v1.2.0^{}`）只用于确定目标 commit，不产生第二个标签候选。

### 3.2 触发与频率（M4a-R1）

| 触发 | 默认 | 行为 |
|---|---|---|
| 手动检查 | **必做** | 工具栏「检查更新」按钮 → 只读检查 → 弹窗呈现四态 |
| 定期检查 | **默认关闭**，显式开关 | 仅在**应用运行期间**按周期执行；只产生提示；开关关闭时无任何活动 |
| 即时检查 | **默认关闭**，可开启 | 安装/更新成功后触发一次只读检查 |

**硬约束**：应用未运行时不检查（无常驻进程/服务/自启动）；任何检查都不得自动执行更新；不存在后台静默路径（可用「无定时器注册」的契约测试复核）。

**T2 落地口径**：两个开关写入 Electron `userData/settings.json`，默认均为 `false`，只有用户切换开关时写入；检查动作本身零写入。`lastCheckAt` 为会话状态，启动时以当前时刻为基线，保证定期检查不会早于启动后 6 小时；应用退出即清除定时器。定期/即时检查只通过 `updates:report` 点亮角标，不弹出阻断式窗口，也不执行 update。

### 3.3 执行：复用 `update` 的边界

| 步骤 | 承担方 | 说明 |
|---|---|---|
| 检查（只读） | GUI 主进程 | 读元文件（只读）+ `git ls-remote` / HEAD；不写索引、不写运行期结论 |
| 用户确认 | 渲染层 | 沿用既有「预览 → 确认 → 带 `--yes`」模式（`App.vue:81`） |
| 执行 | **内核 `update`**（既有指令） | 逐项调用 `update <id> --ref <已确认目标标签>`；复用既有获取、备份、落位与索引刷新路径；保留预演与确认语义 |
| 刷新界面 | 渲染层 | 执行后 `refresh`，沿用既有列表/详情 |

**前置依赖（F1，已关闭）**：远端来源的 `update` refetch 已由 T0 验证可用；执行阶段直接复用既有路径。

**目标标签闭包（T3）**：`--ref <tag>` 仅对远端 git 来源有效；更新前先生成可恢复备份，成功更新后中心库元文件的 `source.ref` 持久化为目标标签，下一次检查以新标签为基线。本地来源、`--check --ref`、非法 ref 按参数类错误拒绝；目标不存在按来源类错误返回且不写状态。无 `--ref` 时既有 update 语义不变。

### 3.4 失败与离线口径（M4a-R4）

| 情形 | 表现 |
|---|---|
| 无网络 / DNS 失败 | 该项 `failed` + `E-SRC-002`/`E-SRC-007` + 可读说明；其余项继续 |
| 认证/限流（403） | `E-SRC-010`，提示「该来源需要认证或已限流，稍后重试」 |
| 超时 | `E-SRC-006`（60 s 上限，与内核一致） |
| 协议不在白名单（含 `file://` 与非回环 `http://`） | `E-SRC-009`，不启动 `git` 子进程 |
| 来源地址内嵌凭据 | 拒绝发起请求（`E-SRC-010`），检查阶段不提示、不保存、不发送凭据 |
| 归档过大 | 仅检查阶段不下载归档，不触发 `E-SRC-008`；执行阶段沿用内核上限 |
| 检查期间磁盘/索引 | **零写入**（只读，可用「检查前后索引字节一致」断言复核） |

### 3.5 签名预留与未来演进

- 检查/比较骨架与「应用是否签名」**完全解耦**：M4a 的检查只读 Skill 来源；
- 若未来立项应用自更新：复用同一套「四态 + provenance + 显式确认」骨架，数据源换成 Release 元数据（`latest*.yml`，需先发布），macOS 需先接入签名/公证（M2 的 5 个 secrets 与条件骨架已留）；本期不实现、不建证书。

### 3.6 GUI 交互（草案）

| 元素 | 内容 |
|---|---|
| 入口 | 工具栏「检查更新」（与「安装」「扫描」并列） |
| 结果弹窗 | 四态分组列表；每项显示「已安装版本 → 可用版本」「来源 URL + ref + 检查时间」「变更摘要」「执行前将先行备份」 |
| 执行 | 每项一个「预览并更新」按钮（走既有预览 → 确认 → `update --yes`）；提供「全部更新」（逐项确认执行，单条失败不阻断） |
| 失败/离线 | 行内说明 + 「重新检查」；不弹阻断式错误 |
| 手动引导 | 沿用既有分发说明（macOS 右键打开 / `xattr -cr`；Linux FUSE）；“应用新版本请从 Release 页下载” |

## 4. 安装形态矩阵（应用自更新，**非 M4a**）

| 平台 / 形态 | 当前可行性 | 结论 | 依据 |
