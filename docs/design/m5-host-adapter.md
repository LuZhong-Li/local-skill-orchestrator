## 1. 设计概述

### 1.1 目标

把 `--target` 的目标标识正式化为**宿主适配层**：一份 Skill 内容（中心库）按各宿主机制渲染为对应格式并落位到该宿主识别的目录；启用 / 禁用 / 更新在宿主之间语义一致；新增宿主只需新增适配器与注册表一行，不改内核 [R-7]。

### 1.2 范围

| 本期设计覆盖 | 不在本期设计范围 |
|---|---|
| 宿主注册表结构与首批注册项 | 宿主侧运行时、加载器、提示词注入（9.5 排除项） |
| 适配器接口、生命周期与内核衔接 | 宿主间双向同步（9.5 排除项） |
| 格式渲染层：字段映射、裁剪策略、降级渲染 | 第三方可加载适配器与扩展点（属 M4b，见第 8 章） |
| 落位扩展：两级粒度、可推导布局、重叠消费处理、与受控副本衔接 | 宿主对格式的实际加载行为验证（属实现期实测，见 2.3） |
| 契约变更清单与登记粒度 | 规则文件类宿主的合并策略细则（留实现期，按写入安全约束） |

### 1.3 设计依据的三层对齐

1. **需求层**：M5-R1 ~ M5-R9 为验收口径，设计不得偏离（第 9 章给出逐条对照表）；
2. **事实层**：调研文档的宿主机制事实与证据等级为唯一事实来源；本文档第 2 章补充的设计前实测为**新增一手证据**，与调研证据同级；
3. **实现层**：设计必须与既有实现对齐——受控副本机制、可推导落位布局、逐文件落位、契约驱动（16 条指令；契约规范由四份增至五份，第五份为本设计落地的宿主注册表规范）。

### 1.4 设计原则

1. **注册表是唯一事实源**：宿主差异只存在于注册表条目，内核与适配器中不得出现未登记的宿主分支 [R-1]；
2. **保守渲染优先**：默认只输出「宿主已确认接受的字段」；未确认字段一律不发（宁可少发，不可发出去被误解或触发宿主校验失败）[R-2] [调研 HR-05]；
3. **可逆与不覆盖**：落位产物可逆；对宿主既有共享文件不得覆盖写入 [R-5] [9.6.2 写入安全约束]；
4. **证据分级驱动**：每个宿主的字段白名单与路径规则都要能指回证据等级；证据不足时降级为「标准字段模式」[R-2] [9.6.2 调研证据约束]；
5. **内置与外部划界**：本期适配器随内核交付、不由外部加载；第三方可加载机制属 M4b，两者不得混用同一套机制 [R-7] [决策点：边界条款见第 8 章]。

## 2. 前置实测结论（设计输入，第 0 步）

四项开放项逐项实测，结论如下。**设计结论建立在这些实测之上**；实测未能覆盖的部分明确标为待确认，并给出影响面与确认方法。

### 2.1 Q-05 标准外字段接受度

| 宿主 | 实测 / 文档结论 | 证据等级 | 对设计的影响 |
|---|---|---|---|
| Claude Code | 认识 16 个字段（含 `when_to_use`、`disable-model-invocation`、`paths` 等扩展），**不认识的字段静默忽略且不报错**；但跨产品路径（claude.ai 上传、Skills API、打包脚本）**只接受标准 6 字段，出现标准外字段硬失败** | [已查证·官方文档] | 渲染层必须支持「标准 6 字段模式」；默认产物即该模式，扩展字段需显式开启 |
| Codex | 本机扫描 165 个已装载技能文件，出现 **27 种** frontmatter 字段（`name` / `description` 全量，另有 `version`、`metadata`、`disable-model-invocation`、`author`、`allowed-tools`、`license`、`compatibility`、`created`、`provenance`、`dependencies`、`activation` 等）且全部正常装载 → **容纳标准外字段** | [已查证·本机实测] | 允许策略存在，但默认仍走标准字段模式；实测字段仅在显式配置下使用 |
| Cursor | 官方文档列出 `name` / `description` / `paths`（`globs` 为旧字段兼容）/ `icon` / `color`，**未说明未知字段处理**；本机未安装该宿主 | [待确认] | 采用白名单裁剪：只发文档列出的字段 [R-2] |
| 豆包 | 本机扫描 `.skills/` 下 174 个技能文件，出现 **21 种** 字段（`name` / `description` 全量，另有 `metadata`、`version`、`requires`、`bins`、`cliHelp`、`license`、`permissions`、`compatibility` 等）→ **容纳标准外字段**；另有客户端校验文案：上传需含 `SKILL.md`、`SKILL.md` 需含 YAML 技能名与描述、**文件名需严格为 `SKILL.md`** | [已查证·本机实测] | 只发标准字段；平台自有字段（`requires` / `bins` / `cliHelp` / `permissions` 等）**不由本工具生成**（语义未知，属宿主自有契约） |

补充观察：Codex 侧 `disable-model-invocation` 的 12 处取值**全部为 `false`**，且这些技能均出现在模型可见清单中，因此**无法判定 Codex 是否对该字段施加语义** → 该字段不得作为跨宿主控制手段，列为待确认（见 2.4）。

### 2.2 Q-06 副本改名禁用表达（三端）

现行实现（`kernel/core/metadata/constants.ts`、`kernel/store/library-fs/index.ts`）：元数据文件名为 `SKILL.md`，禁用后缀为 `.disabled`，禁用即把副本内 `SKILL.md` 改名为 `SKILL.md.disabled`，只做文件改名、不动目录。

| 宿主 | 结论 | 证据等级 | 说明 |
|---|---|---|---|
| Claude Code | **成立**：技能身份取决于目录内存在 `SKILL.md`，且 frontmatter 仅在该文件首行为 `---` 时解析 | [已查证·官方文档] | 改名后该目录不构成技能 |
| Cursor | **成立**：文档表述为「递归查找任意 `SKILL.md`」 | [已查证·官方文档] | 改名后不被拾取 |
| 豆包 | **成立**：客户端校验规则要求「文件夹需在下一级包含 `SKILL.md`」「文件名需严格为 `SKILL.md`」 | [已查证·本机实测] | 改名后不满足校验规则；运行时是否即时丢弃待确认 |
| Codex | **结构上成立，待实测**：技能目录以 `SKILL.md` 为载入点（本机实测结构），但未观测到宿主再扫描行为 | [已查证·本机实测 + 待确认] | 见 2.4 |

共同缺口：**宿主何时重新扫描**（新会话 / 重启 / 热加载）未实测。影响面：`enable` / `disable` 的生效延迟与输出提示文案（是否需要提示「重启该宿主后生效」）。确认方法见 2.4。

### 2.3 Q-07 豆包两级技能根

| 观测项 | 实测结果 | 证据等级 |
|---|---|---|
| 工作区顶层结构 | 仅两个条目：`.skills/` 与 `.user_skills/` | [已查证·本机实测] |
| `.skills/` | 141 个技能目录，含 `name` / `description` 等 frontmatter；目录修改时间为**当日**（平台刷新迹象） | [已查证·本机实测] |
| `.user_skills/` | 目录存在但**当前为空**，创建时间早于 `.skills/` 的最近刷新时间（安装期创建） | [已查证·本机实测] |
| 客户端代码线索 | `MOA_USER_SKILLS: "131"` 为上传场景枚举值，**不是路径常量**，不能据此判定加载逻辑 | [已查证·本机实测] |
| 运行期技能根列表 | 宿主技能发现机制列出的技能根为**多个**：`.skills/`、`.user_skills/`、`.agents/skills/` —— 即 `.user_skills/` 与 `.skills/` 同级并列、都会被扫描 | [已查证·运行期证据（用户提供）] |
| 目录权限属性 | `.skills/` 为只读（平台持有）、`.user_skills/` 用户可写且为空 | [已查证·运行期证据（用户提供）] |
| T0 机械实测（本机） | 在 `.user_skills/` 放置最小测试技能（名称与目录名一致、UTF-8 无 BOM、LF），创建成功；`.user_skills` 目录时间戳更新，`.skills/` 计数与时间戳未变；实测后现场已恢复（剩余条目 0） | [已查证·本机实测] |

**结论（T0 后定稿）**：两级技能根并存且**都被扫描**；**用户技能落位根 = `.user_skills/`**（可写、可加载、当前为空），`.skills/` 由平台持有（只读、平台维护）**禁止写入**。本机 ACL 属 Windows 语义，看不出「只读 / 可写」的权限差异（两侧均为当前用户 FullControl），故权限结论以运行期属性证据为准 [HD-04]。

**第三技能根 `.agents/skills/`**（运行期列表提及，本机工作区内**不存在**该目录）：若该根本身也被豆包扫描，则它与 Cursor 的 `.agents/skills/`（项目级 / 用户级）是**同一路径**，会构成跨宿主共享落位根——属 M5-R8 的重叠消费情形。列为 HD-07，不影响本期豆包落位根的选择（默认仍为 `.user_skills/`）。

| `doubao` | skill 机制（工作区 `.skills/` / `.user_skills/`，两级均被扫描） | confirmed | [已查证·本环境实测 + 运行期证据] | skill：`<工作区>/.user_skills/<Skill 标识>`（**已确认的用户落位根**）；**禁止写入 `.skills/`**；`.agents/skills/` 待 HD-07 | `standard6`；平台自有字段不生成 |
| `agentskills`（通用条目） | 标准符合型产物（不绑定具体宿主） | confirmed | [已查证·官方标准站] | skill：由调用方指定落位根（缺省不落位，仅产出产物） | `standard6` |
| `agents-md`（通用条目） | 指令文件载体（降级） | confirmed | [已查证·官方格式站点] | rules：`AGENTS.md`（根或子目录，写入需合并策略） | 降级渲染（条目段落），无字段 |
| `deepseek`（登记但不适配） | 无 skill 机制，模型提供方 | not_applicable | [已查证·官方文档] | — | 无（登记为不适用；如需分发只能降级为 `agents-md`） |

说明：`cursor` 的两种路径类**分两条注册项登记**（同一宿主、不同 `roots.kind`），对应 [R-9] 的「两级粒度」；`agentskills` 与 `agents-md` 是通用条目，不是宿主，`--target` 取值是否暴露给用户由第 7 章的决策点裁定。

### 3.3 新增宿主流程（零内核改动）

1. 在注册表新增一行：填 `host_id`、三维分类、`roots[]`、`capability`、`render_policy`、`evidence`、待确认项；
2. 若该宿主符合已有渲染形态（标准 skill / 规则文件 / 降级载体），**只加注册表一行即可**；
3. 若需要新的字段映射或落位形态，则新增一个适配器实现，并挂到 `adapter_ref`；
4. 校验：注册表结构校验 + 该宿主的格式合规校验纳入 M1 门禁；
5. 验收口径：变更范围只有注册表条目与适配器（不改内核分支）[R-7]。

## 4. 适配器接口设计

### 4.1 接口签名（设计约定，不含实现）

```text
interface HostAdapter {
  readonly hostId: string;                     // 与注册表 host_id 一致
  describe(): HostDescriptor;                  // 返回注册表条目视图（只读）
  render(input: RenderInput): RenderOutput;    // 渲染：内部规范 → 宿主格式（纯函数、确定性）
  plan(input: PlacementInput): PlacementPlan;  // 生成落位计划（不写盘）
  verify(plan: PlacementPlan): Finding[];      // 只读校验：结构、格式、字段合规
  cleanup(plan: PlacementPlan): CleanupPlan;   // 生成可逆回收计划（删除或条目摘除）
}

type RenderInput   = { skill: SkillContent; policy: RenderPolicy; target: TargetRef }
type RenderOutput  = { files: ArtifactFile[]; droppedFields: FieldNote[]; notes: string[] }
type PlacementPlan = { root: RootRef; entries: PlacementEntry[]; conflicts: ConflictNote[] }
type Finding       = { level: 'error' | 'warning'; code: string; where: string; remedy: string }
```

要点：

1. `render` 为**纯函数**：输出只依赖 `skill` / `policy` / `target`，同一输入重复渲染结果一致，且不修改中心库 [R-2]；
2. `droppedFields` 必填：任何被裁剪或改写的字段都要显式回报，供输出与登记使用（不得静默丢弃）[R-5]；
3. `verify` 只读，产物校验不写入任何文件 [既有 NFR-01 只读口径]；
4. `cleanup` 只产出计划，实际写入由内核既有编排执行（保持「计划 → 确认 → 执行」的既有形态）。

### 4.2 生命周期

| 阶段 | 触发者 | 行为 | 失败处理 |
|---|---|---|---|
| 选择 | 内核解析 `--target` | 按注册表解析出「宿主 + 路径类」，取出适配器 | 取值未登记 → 既有错误码，不落位 [R-3] |
| 渲染 | 内核编排 | 调用 `render`，得到产物与字段差异清单 | 渲染失败 → 中止，环境不变 |
| 落位 | 内核编排 | 由 `plan` 生成计划，经既有受控副本与逐文件落位写入 | 沿用既有原子性与回滚 |
| 校验 | 内核编排 | 调用 `verify`，结果进入结果封装 | 校验不过 → 报告并保留现场 |
| 可见性 | `enable` / `disable` | 技能根类宿主复用既有副本改名原语；规则路径类宿主走条目插入 / 摘除（可逆） | 见 6.4 |
| 清理 | `uninstall` / `restore --list` 等既有路径 | 调用 `cleanup` 生成回收计划 | 沿用既有备份先行 |

### 4.3 与既有内核的衔接

1. **挂载层**：适配器属内核侧能力，位于「生命周期编排层」之下、「文件存储层」之上的适配层；内核不感知任何具体宿主名，只通过注册表 + 适配器接口工作 [R-1] [R-7]；
2. **选择机制**：`--target` 取值 → 注册表条目 → `adapter_ref` → 适配器实例（同一适配器可服务多个宿主标识，例如标准形态的多个宿主）；
3. **复用既有能力**：受控副本、可推导布局、逐文件落位（`file_map`）、原子写入、备份先行、只读校验全部复用，适配器**不自行实现写入**；
4. **渲染与落位解耦**：渲染产物（文件集合）与落位计划（目标路径集合）分离，便于 `--preview` 只产出计划、不写盘 [既有预演能力]。

## 5. 格式渲染层设计

### 5.1 字段映射表（内部规范 → 标准 6 字段 → 各宿主）

| 内部字段 | Agent Skills 字段 | Claude Code | Codex | Cursor | 豆包 |
|---|---|---|---|---|---|
| `id` / 目录名 | `name` | 发（必填，须与目录名一致） | 发 | 发 | 发 |
| `description` | `description` | 发（≤1024 字符；列表展示另有截断） | 发 | 发 | 发（平台校验要求 YAML 含技能名与描述） |
| `license` | `license` | 发 | 发（实测容器接受） | 裁剪（文档未列） | 发（实测出现 9 次） |
| `compatibility` | `compatibility` | 发（≤500 字符） | 发（实测出现） | 裁剪 | 裁剪（实测出现 3 次，语义未确认） |
| 扩展元数据映射 | `metadata` | 发 | 发（实测出现 18 次） | 裁剪 | 裁剪 |
| 扩展元数据.版本 | `metadata.version` | 发（引号包裹） | 发 | 裁剪 | 裁剪 |
| 扩展元数据.作者 / 主页 / 标签 | `metadata.*` | 发（标签转字符串） | 发 | 裁剪 | 裁剪 |
| 扩展元数据.依赖声明 | `metadata.*` + `compatibility` 文本 | 拆分 | 拆分 | 仅 `description` 内提示 | 仅 `description` 内提示 |
| 允许工具 | `allowed-tools` | 发（实验性，须标注） | 发（实测出现 7 次） | 裁剪（文档未列） | 裁剪 |
| `trigger_keywords` | —（无标准字段） | 并入 `description`（受长度上限约束） | 同左 | 并入 `description` 或 `paths` | 并入 `description` |
| `status` / `path` / `targets` / `source` | —（管理器侧概念） | 不发（不进宿主格式） | 不发 | 不发 | 不发 |

补充规则：

1. 「裁剪」= 字段保留在内部规范与索引中，不写入宿主产物，并进入 `droppedFields` 报告 [R-5]；
2. 平台自有字段（豆包的 `requires` / `bins` / `cliHelp` / `permissions`，Codex 的 `agents/*.yaml` 界面声明）**不由本工具自动生成**；用户可在扩展元数据中显式声明透传，但只走 `host_declared` 的**宿主透传白名单**（裁决 DP-04，细则见 5.2）[调研]；
3. Claude Code 扩展字段（`when_to_use`、`argument-hint`、`disable-model-invocation`、`context`、`paths`、`hooks` 等）默认**不渲染**；原因：跨产品路径会硬失败，且其他宿主语义未知 [2.1] [HR-05] [HD-02]。

### 5.2 渲染模式

| 模式 | 字段范围 | 适用 |
|---|---|---|
| `standard6`（默认） | 仅标准 6 字段 | 全部首批宿主；跨产品发布路径 |
| `host_declared` | 标准 6 字段 + 该宿主注册表中声明且证据充分的扩展字段 | 仅在用户显式开启且注册表已登记该扩展时 |
| `degrade_entry` | 无字段；名称 + 描述 + 正文折叠为条目段落 | 规则文件 / AGENTS.md 载体 |

渲染确定性、幂等与「不修改中心库」为三种模式的共同前置 [R-2]。

**透传白名单细则（裁决 DP-04）**：

1. **白名单来源**：各宿主注册表 `render_policy.allowed_extensions[]`，取值来自该宿主的**实测字段集**（Codex 实测 27 种、豆包实测 21 种，均为本机实测且全部正常装载）。白名单只登记**标准 6 字段之外**的字段：Codex 为 20 项、豆包为 15 项——标准字段由渲染模式直接输出，禁用字段 `disable-model-invocation` 一律排除；
2. **命中即透传，未命中即忽略并警告**：白名单外的字段不写入产物，且必须回报警告（进入 `droppedFields` 与输出载荷），不得静默丢弃 [R-5]；
3. **Claude 的白名单为空**：跨产品路径（claude.ai / Skills API / 打包脚本）对标准外字段**硬失败**，故 Claude 适配器一律只发标准 6 字段 [Q-05]；
4. **`disable-model-invocation` 禁止透传**：该字段在各宿主语义不明（Codex 侧 12 处取值全为 `false`，无法判定是否施加语义），登记为「宿主自有字段、不透传」，任何宿主白名单都不得包含它 [HD-02]；
5. 启用 `host_declared` 时，产物必须携带「本次透传了哪些非标准字段」的记录，便于问题定位与宿主升级后的回归比对。

### 5.3 共用渲染核心

通用 Agent Skills 标准目标与逐宿主适配器**共用同一渲染核心**，差异仅在字段裁剪策略（`standard6` vs `host_declared`）与落位根绑定 [R-4]。实现上表现为：一个渲染核心 + N 组策略，而不是 N 套渲染实现。

### 5.4 降级渲染规则（规则文件 / 指令文件载体）

| 目标形态 | 产物 | 规则 |
|---|---|---|
| Cursor 规则路径 | `.cursor/rules/<Skill 标识>.mdc` | frontmatter 三要素 `description` / `globs` / `alwaysApply`；正文为技能正文的条目化摘要；必须以可逆方式新增，不得修改既有 `.mdc` [9.6.2 写入安全约束] |
| 通用指令文件载体 | `AGENTS.md` 条目段落 | 纯 Markdown 条目（技能名 + 描述 + 使用指引）；**写入宿主既有文件前必须具备合并策略**，策略未定稿时只产出待合并片段，不落盘 [R-5] [9.6.2] |
| 无机制宿主 | 无产物 | 登记为 `not_applicable`，仅在输出中提示（不静默落位到宿主不读取的位置）[R-5] |

能力差异声明（强制）：降级产物必须同时回报「本形态不提供的能力」——自动发现、按需加载、工具预授权三者固定列入 [R-5]。

## 6. 落位扩展设计

### 6.1 `--target` 两级粒度

`--target` 取值解析为「宿主 + 路径类」两级 [R-9]：

| 路径类 | 含义 | 路径来源 | 首发覆盖 |
|---|---|---|---|
| `skill`（技能根） | 技能形态宿主识别的技能目录 | 可推导布局 `.<目标标识>/skills/<Skill 标识>` | claude、codex、cursor |
| `rules`（规则路径） | 规则文件宿主识别的规则位置 | 注册表 `roots[].path_template` 单独登记（不适用可推导布局） | cursor（`.cursor/rules`）、agents-md |
| `external`（工作区外技能根） | 宿主在工具工作区之外维护技能根（如豆包 agent 模式工作区、Codex 用户目录） | 注册表登记的绝对/家目录相对模板 | doubao（`.user_skills/`，已确认） |

取值表达方式（**决策点 DP-01**）：

- **方案 A（推荐）**：注册项即路径类，标识即路径前缀——`claude`、`codex`、`cursor`（技能根）、`cursor-rules`、`agents-md`、`doubao`。理由：可推导布局已把标识当作路径前缀，方案 A 不引入新语法、不破坏既有不变量；
- 方案 B：复合取值 `cursor:rules`。代价是引入新的取值语法与转义规则，需同步修改取值校验。

无论采用哪种方案，**实施前必须把粒度写入指令契约规范**（取值范围、绑定关系、未登记取值的错误处理），且不新增指令、不新增选项 [R-9]。

### 6.2 可推导布局与规则路径的关系

1. 技能根类沿用既有不变量：副本目录必须等于 `.<目标标识>/skills/<Skill 标识>`，元文件中的 `path` 与约定不一致即拒绝登记 [既有 3.5 约定]；
2. 规则路径类**不参与**可推导布局：其位置由注册表 `roots[].path_template` 给出，且必须在注册表中可查（否则视为未登记路径）[R-3]；
3. 规则路径类的写入必须是「可逆新增」：独立文件可整文件回收；共享文件内的条目段落必须可精确定位并摘除 [R-5]。

### 6.3 重叠消费处理

1. 定性：**特性而非冲突**——一次落位服务多个宿主 [R-8]；
2. 注册表声明每个落位根的**消费宿主集合**（如 `.claude/skills/` 被 `claude`、`cursor` 消费；`~/.codex/skills/` 被 `codex`、`cursor` 消费）[R-8]；
3. 硬约束：不得因重叠拒绝落位；不得为同一宿主重复产出副本（同一 Skill 在同一宿主下只允许一个副本）[R-8]；
4. 重叠关系必须**只声明、不推断**：消费集合来自调研证据，未登记的关系视为登记缺陷 [R-1] [R-8]；
5. **决策点 DP-02**：是否在落位时检测重叠并提示（例如「此次落位将同时被 Cursor 识别」）。需求层未规定，本设计建议**默认静默、在详情输出中列出消费宿主**（避免噪音），实现期可配置为提示。

### 6.4 与受控副本衔接：启用 / 禁用 / 更新

| 路径类 | 启用 / 禁用表达 | 依据与限制 |
|---|---|---|
| 技能根（claude / codex / cursor） | 沿用副本内 `SKILL.md` ↔ `SKILL.md.disabled` 改名；不改动任何目录 | 三端「技能身份 = 目录内 SKILL.md」均已查证 [2.2]；生效时机见 HD-03 |
| 技能根（豆包） | 同上（改名后不满足平台「严格 `SKILL.md`」校验） | [已查证·本机实测] |
| 规则路径（cursor-rules / agents-md） | 条目级插入 / 摘除（可逆）；共享文件不得覆盖写入 | 合并策略未定稿前只产出片段，不落盘 [9.6.2] |

更新流程沿用既有顺序：**先按各自适配器重渲染副本、再写索引**；单宿主失败不影响其他宿主 [R-6]。

## 8. 与 M4b 的划界确认

| 维度 | 本期（M5，内置适配器） | M4b（外部扩展机制） |
|---|---|---|
| 交付形态 | 适配器随内核交付；注册表条目由内核维护 | 第三方可加载的扩展与其清单、注册协议 |
| 加载方式 | 编译期内建，通过 `adapter_ref` 引用 | 由扩展点加载外部实现 |
| 扩展新宿主 | 加注册表一行（+ 必要时一个适配器） | 由第三方提供扩展包并由加载器装载 |
| 冲突风险 | — | 若把 M5 的适配器当作「插件先例」，会混淆内置与外部两条机制 |

边界条款：**两条机制不得共用同一套注册、发现与加载路径**；M4b 若立项，其扩展点设计不得以 M5 的适配器接口为对外契约 [R-7] [9.3.5]。宿主注册表是内核资产，不构成对外扩展接口。
